# Architecture

The subsystems behind the rooms and games, in detail. `CLAUDE.md` keeps one line on each; read the section here before changing that subsystem, and update it in the same change.

## Drawing canvas

Code: `packages/game-sdk/src/drawing.ts`, `packages/ui/src/drawing.tsx`; `docs/adding-a-game.md` "Drawing".

Vector strokes on an 800 × 1000 page, four named colour-blind-safe pens and an eraser (`ERASER`, a stroke that masks the ink before it), three widths, encoded compactly (`encodePoints`) and checked in `reduce` with `validateDrawing`. `DrawingPad` draws (undo, clear, a draft under `storageKey`, `sendBy` before a strict deadline, palm and second-finger handling); `DrawingView` shows a drawing read-only at any size. Drawings live in game state and `view()` sends only those a viewer needs.

## Sound panel

Code: `packages/ui/src/sound/`.

Every game with sound shows the same per-player volume sliders, 0–100 % (0 is off): a master and one per type it plays (`music`, `effects`, `voice`), each with a ▶ preview of that game's own clip. Volumes are kept per device and seat (`useVolumes(game)`, `storageKey('vt.<game>.volumes')`), every slider at 50 % out of the box (`DEFAULT_VOLUMES`, the table screen's too; volumes stored without the `reset` mark read as the defaults once); a sound plays at master × its type (`gainOf`), but only where a device shows more than one type: with a single slider no master shows and it counts as 100 % (`masterShown`, `heardVolumes`), so that slider, its ▶ and the summary are the real volume. A player gets only the sliders for sound that plays on their device under the host's choice (`soundPlan`: Off, Host's device, Every device, Table screen), with `whereLine` saying where it plays; the table screen has no input, so the host sets its volumes through the game's `table-volume` action (`tableVolumeAction` in `@vt/game-sdk`). The lobby has a folded "Sound" section (`LobbySound`) and play a 🔊 corner (`SoundButton`). Nothing musical plays in the lobby (phase `lobby`; the ▶ previews still do). The host chooses whose volume their own sliders set ("My sliders set: Just me / Everyone", `hostMode` from `useVolumeShare`; kept per room as `hostVolumes.mode`, a saved room reads as "Just me", and switching pushes nothing). With "Everyone" the `host-volume` action (`hostVolumeAction`, `hostVolumeChange`) keeps each level with a version in the settings' `hostVolumes` (and on the table screen's volumes), every device takes each change into its own stored volumes once (`useHostVolumes` in the game's root, versions under `vt.<game>.volumes.host`), a player's own change after that sticks until the host moves that slider again, and others' sliders say "Set by the host" for a moment (`useVolumeShare`).

## Colours

`apps/web/src/index.css` defines semantic tokens (`page`/`panel`/`card`/`line`, `accent`, `info`/`warn`/`danger`/`success`/`special` soft tints, `team-a`/`team-b`) that are warm and muted in light mode and map to the old stock values in dark mode, which must stay unchanged. `light-palette.css` (generated by `scripts/light-palette.mjs`, checked by its test) mutes Tailwind's chromatic scales in light mode only. UI code uses the tokens: `light-mode.test.ts` rejects light-mode chromatic fills, rings, borders and outlines, except lines marked `vt-palette` and Hydra's edition scales. See `docs/adding-a-game.md` §3.

## Rules guides

Each game's `GameGuide` (`src/logic/guide.ts`) renders on `/rules/:gameId` and in the in-room rules drawer through `apps/web/src/components/GuideView.tsx`, in four tabs: Learn (goal + a 4–7 step stepper, which is also the lobby's one-time intro), the game's tiles (an optional `catalog` adds a Cards tab), Rules (sections banded `basics`/`details`/`edge`, greyed "Not in this game" when their `option` is off) and Cheat sheet. The drawer passes the viewer's own view to the guide's `room()`; the rules page offers `presets` instead. Back-room guides are `makeGuide(names)` + `nameGuide(manifest)` so real names, card text and art come only from the manifest (`private.test.ts` checks no stand-in survives). See `docs/adding-a-game.md` §2. Update the guide in the same change as any rule change.

## Table screen

Code: `apps/server/src/stage.ts`, `routes/stage.ts`, web `pages/StagePage.tsx`, `pages/StageShowPage.tsx`, `stage/`, `components/TableScreen.tsx`; `docs/adding-a-game.md` "Table screen".

One per room, game-agnostic. Only the host pairs it (`room:stage-code`: 6 characters from `STAGE_CODE_ALPHABET`, 10 min, single use, in memory, at most 5 open per room) and removes it (`room:stage-remove`); `POST /api/stage/pair` (rate-limited) sets the signed `vt_stage` cookie `<roomId>.<nonce>.<back-room version>.<issued>` (7 days), valid while the room's `stage` column holds that nonce, so pairing again or removing it kills the old pass. The TV joins with `room:join` `{ roomId, role: 'stage' }`: no seat, no actions, never presence, host, sweep, live count or stats; it gets `view(state, null)` (`snapshot.role: 'stage'`, `you: ''`), and every snapshot has `stage: { present }`, which the shell turns into `GameUiProps.profile` (phones go `phone-quiet`). The pass is re-checked on every broadcast like an unlock. For a back-room room it is that room's unlock only: its own game's art and manifest and the `/backroom-assets/` code chunks, never `/api/games`, the status, decks, other games, rooms or recaps, and a new back-room word kills it. In a playtest the admin's session opens it without a code. A game opts in with a lazy `ClientGame.stage`; others get `GenericStage`.

## Player colours

Every player has a colour per room (`RoomPlayer.color`, the 16 `PLAYER_COLORS` in `packages/game-sdk/src/colors.ts`, each with a screen-reader name), saved in the room's players JSON (`rooms/colors.ts`). Joining gives a random colour nobody has (past 16 people, one of the least used); `room:recolor` changes it at any time, mid-game too (through the game's `playerJoined`), and refuses one someone else has. A game may limit its rooms to a list (`GameDefinition.colors`, `colorsOf`; Going Once's seven): joins, playtest seats and bots get only those, others are refused (`color-not-offered`), and a loaded room moves anyone outside the list onto a free one (`withColors`). `PlayerTag` draws the dot from the shell's `PlayerColors` context; the picker is in the Players drawer and behind `GameUiProps.pickColor`. Stats and recaps never see colours.

## Room shell helpers for games

See `docs/adding-a-game.md` §3.

`waitingFor`/`waitingForHost`, `Countdown` (`label`, strict/soft captions), `useSpectatorPrompt`, `act(action, { anchor })` with a `RefusalSlot` for refusals next to their control, `StickyBar` to keep Start reachable on phones, `Standings` for the shared end screen, and `EndTabs`, which splits an end screen on phones (below `lg`) into tabs so it fits a 390 × 844 phone. The snapshot's `hostAwayUntil` drives the "host is away" banner. A code chunk that fails to load after a deploy reloads the page once (`apps/web/src/lib/chunk-reload.ts`).

## Game settings

Code: `GameSettingsStore` in `apps/server/src/game-settings.ts`, `routes/games-admin.ts`, types in `packages/protocol/src/game-settings.ts`, the admin's `/tavern-keeper/games`.

One record per game (`enabled` and `categories` for all, `title` for back-room games, `music` for games whose definition declares `music.phases`), plus the category list. All of it lives only in the database, never in code: `game_settings` in `app_settings`, while titles and music keep their old keys (`private_game_titles`, `private_game_music`). Everything that names or plays a game reads through the store; stats and recaps name games through `gameNamer` (the DB title where one is set, else the code name, applied when served). A game that is off leaves the lists and chips (`GameSummary.off`), `POST /api/rooms` refuses it (`game-off`), and the room manager's `gameOff` lets open rooms finish their game but refuses another; playtests are never stopped. `/api/games` gives each game its categories with an `order` among the categories of the games that browser can play, so a locked browser learns nothing of back-room games (tested). `scripts/set-game-title.mjs` and `scripts/set-game-categories.mjs` apply titles and categories after a game goes live.

## Question decks

Code: `question_decks`, `QuestionDeckRepo` in `apps/server/src/question-decks.ts`.

Hold questions for games that set `usesQuestionDecks`, mirroring word lists: a `games` array (default `["hoodwink"]`; the admin API accepts only registered games that set `usesQuestionDecks`), an `enabled` switch, and `forGame(id)` merged into the per-room `ctx.content` (`roomContent`). Each question is `{prompt, answer?, alternates, sources, adult, tags, decoys?, hints?}`, with ids `<deckId>:<index>`; the rules live in `packages/protocol/src/questions.ts` and are repeated in `scripts/import-question-decks.mjs`. A deck's kind comes from its tags: **trivia** decks (games without `questionKind`, i.e. Hoodwink) need an `answer` and the `___`/`?` prompt shape (`triviaProblem`), **open** decks (games with `questionKind: 'open'`, i.e. Stampede; the script's `OPEN_GAMES` mirrors it) have no answer, alternates or decoys and optional `hints` (common answers, for playtest bots only, through `BotCtx.hints`; never in a room's state or an HTTP response except the admin detail and export); a deck tagged for both kinds is refused, and a PUT without `games` keeps the stored deck's kind. Trivia games get `ctx.content.questions()`, open games `ctx.content.openQuestions()` (prompts only). **The decks are private content: never commit them** (not even as fixtures; tests use small made-up decks). They live only in the production database, are imported with `scripts/import-question-decks.mjs` (see `docs/deployment.md`) and backed up from `/tavern-keeper`. Only back-room games use them: deck summaries are served at `GET /api/backroom/question-decks/:gameId`, which answers 404 unless the browser has the back room and the game is private with `usesQuestionDecks`. No public endpoint returns deck names, and answers, sources and decoys never appear in an HTTP response except the admin detail and export (rooms get them through `ctx.content.questions()`, and `view()` must hide them).

## Built-in word packs

Packs are `apps/server/word-packs/<slug>.json` (`{slug, name, description, games?, words}`; file name must match the slug; entries ≤ 20 chars, or ≤ 40 when every game in `games` is a phrase game (`PHRASE_GAMES` in `word-packs.ts`); ≥ 100 unique words). A pack with `games` is tagged only for those games; without it, for every word-list game. On startup `WordListRepo.seedPacks` adds any pack whose slug isn't in `seeded_packs` yet, exactly once, so admin edits and deletions stick. Changing a shipped pack's file does not update existing databases; add a new slug instead.

## Content packs

Code: `content_packs`, `ContentPackRepo` in `apps/server/src/content-packs.ts`, admin routes in `routes/content-packs.ts`, types in `packages/protocol/src/content-packs.ts`.

Private content for back-room games that need more than words or questions. A game declares `contentPacks: { kinds: { <kind>: schema } }`; the admin API takes only registered private games, their declared kinds and data their schema accepts, and rooms read every enabled pack of a kind through `ctx.content.contentPacks(kind)`. **Packs are private content: never commit them** (tests use made-up packs). They are imported with `scripts/import-content-pack.mjs` (`docs/deployment.md`; `--replace` updates a pack in place, keeping its id) and managed on `/tavern-keeper`. Markup never reaches a room: pack schemas pass every string through `plainText` (`@vt/game-sdk`, plain JS in `markup.mjs` so the script imports the same file), and the script does the same before sending. Lint refuses hand-rolled tag stripping, as it does hand-rolled RegExp escapes. No route but the admin's returns pack data (`routes/content-packs.test.ts` crawls every GET route as an unlocked browser).

## Admin stats

Code: `apps/server/src/stats/`.

The room manager reports every change to an optional `RoomObserver`; `StatsRecorder` turns that into flat events (game start and end are detected generically from `phase`), buffers them and writes every 2 s. A game's length is its active play time (gaps over `BREAK_AFTER_MS` count 0); data and day buckets are UTC, the page shows the viewer's time zone. A failing observer is logged and never reaches play. Games may add a pure `insights(before, after, action, by)` returning `InsightEvent`s, which feed the per-game figures and fun facts in `stats/figures.ts`. Storage sits behind the `StatsStore` (write) and `StatsQueries` (read) interfaces. Rollups and raw-day queries share one aggregation (`stats/aggregate.ts`), so a rolled-up day must read exactly like its raw events (tested). Routes are `/api/admin/stats/*`, typed by `packages/protocol/src/stats.ts`, the single source of truth for both sides: `percent` figures are 0–100, and responses name every game they mention so the page needn't unlock the back room. The event props each game emits must match what `figures.ts`/`aggregate.ts` read; `routes/stats.test.ts` plays real games to keep them in line. Chart colours come from a fixed per-game order in `apps/web/src/stats/palette.ts`: append new games at the end so existing colours never shift. The page is `/tavern-keeper/stats`, a lazy chunk with ECharts in its own chunk. Retention, export and reset are covered in `docs/deployment.md`.

## Tavern night recap

Code: `apps/server/src/recap/`.

Each game's `awards` module (`src/logic/awards.ts`, contract in `packages/game-sdk/src/awards.ts`) reads that game's own insight events. `night.ts` splits a room's `stats_events` into nights (finished games under 3 h apart, at most 16 h, split by the host's `room.wrapped`); `engine.ts`/`select.ts` score the candidates (seeded, so every viewer gets the same card) into each game's strip, the night card and "Past rounds"; `night-awards.ts` holds the cross-game awards. `RecapService` answers the member-only socket events `room:recap`, `room:wrap` and `room:recap-tone` (host only), flushing the stats recorder first. Text carries placeholders (`{p:id}`, `{role:id}`, `{loc:id}`, `{card:id}`) the browser resolves (`apps/web/src/recap/`, private names through `ClientGame.labels`). The room's tone and host time zone live in `room_recap_settings` (not a stats table, so the stats reset keeps it); the admin kill switch is `recap.enabled` in `app_settings`. Copy rules are checked by `recap/copy.test.ts`; see `docs/adding-a-game.md` §1b.

- **Hall of fame and frozen nights** (`recap/hall.ts`): a night is frozen into `recap_nights` (both tones, plus a public-only variant when a public room's linked night reached the back room) when the host wraps it up or the room's next night starts, and a frozen card is served as it was, never recomputed. `recap_awards` feed the Hall of fame and the freshness penalties in `select.ts`; `recap_records` keep each room's best value of the nuggets marked `record`. These are not stats tables: the stats reset leaves them, a swept room's rows go with it, and "Forget me" scrubs the player from them.
- **Linked nights** ("Same crew, new game"): `POST /api/rooms` takes an optional `nightKey`; the creator must be in a room of that night (`RecapService.linkable`), and the old room gets `room:next` so the crew can follow. A game with the optional `carry(state)` hook (Mission Control's campaign) hands the new room what the night's latest room of the same game carries, as `ctx.carried` in `create`. `night.ts` merges every room sharing the key into one night; a viewer without the back-room unlock never sees a back-room table's games, not even as a count.
- **Save image** (`apps/web/src/recap/image.ts`): a hand-drawn Canvas 2D card (text and emoji only, never private art); neither it nor "Copy for chat" carries a link. Games show as their own emoji (`ClientGame.icon`, one per game, never 🍺 or 🎲, checked in `private.test.ts`).

## Playtests

Code: `/tavern-keeper/playtest`, `routes/playtest.ts`, admin only.

The admin plays any game, back-room ones included, from tabs of one browser, one tab per seat.

- **Seats:** `minPlayers` to `seatLimit(game)` (the game's `maxSeated`, else `maxPlayers`, capped at `MAX_PLAYTEST_SEATS`). `POST /api/admin/playtests` creates the room (`rooms.playtest`, and `test: true`, so every stats and recap skip applies) and seats every seat server-side with a fresh token. Seat links carry the token in the URL fragment (`/r/<id>#seat=…&as=…`); `apps/web/src/lib/seat.ts` keeps it in sessionStorage per room id and honours it only when `/api/rooms/:id` says `playtest: true`.
- **Gate:** a playtest is the admin's alone. `/api/rooms/:id` answers 404 to anyone else, and `room:join` answers `no-room` unless the socket carries a current `vt_admin` session (re-checked on every action and broadcast; logout revokes the session on the server, so open seat tabs lock at the next change).
- **Stats safety:** test rooms never reach `liveRooms()` or the Live tab's socket count. `PlaytestPreview` (`rooms/preview.ts`) works out a finished game's award strip in memory and sends it as `room:playtestAwards`; nothing is written.
- **End:** `DELETE /api/admin/playtests/:id` (or the host seat's TEST bar) sends `room:closed` and deletes the row; `sweepPlaytests` deletes playtests with no seat connected for 15 minutes.
- **Bots:** a game's optional `bot(view, ctx)` hook (`docs/adding-a-game.md` §1c) plays a seat from that seat's own `view()` only. `BotRunner` (`rooms/bots.ts`) moves only in a playtest with a human seat connected and bots not paused, after a short pause times the speed, recomputing the move when it fires and sending it through `act`. A refused move waits for the next change (or retries when `botInfo.retry(code)` allows); `botInfo.quick(move)` marks moves that wait only a button press's pause; a runaway bot is rate-limited and then paused (`stuck`). Bot ids come from discarded tokens, so nobody can join as one; bots show as connected (`RoomPlayer.bot`) but never count as presence for host hand-off, the sweep or the live view, and never host. Codenames, Echo, Enigma, Iconic, Séance and Hydra have no bot (Inquest's bots never take the Forensic Scientist, which `botInfo.setup` gives to the host).
- **Per-seat storage:** game UIs build localStorage keys with `storageKey(base)` from `@vt/game-sdk`, which the room shell scopes to the seat in a playtest.

## Edge cache

Code: `apps/edge`, a Cloudflare Worker on `/backroom-assets/*` and `/api/backroom/assets/*`.

It serves back-room code (filled from origin) and art (from the R2 binding) out of Cloudflare's cache, keyed by URL alone, but only to a browser whose `vt_edge` pass it verifies (HMAC with `EDGE_SECRET`, the unlock's lifetime, the password version from `/api/edge/backroom-version`); anything else, every error included, goes to origin untouched (origin answers without a cache header, and the server's back-room refusals, leave as `private, no-store`), so it never refuses anyone. The Worker's own Workers Caching setting stays off: it runs before the pass check, keyed by URL alone. The server issues the pass with every unlock when `EDGE_SECRET` is set (`apps/server/src/edge.ts`, its own secret, never the session secret) and clears it on lock; the shared names are in `@vt/protocol/edge`, and the Worker's `assetKey` must match the server's (tested). Setup and rollback are in `docs/deployment.md`. Opening a room has timeouts and retries on every step (`lib/retry.ts`, `JoinWatch`), each step named with a reload offer after 15 s (`LoadingStep`).

## Metrics

Code: `apps/server/src/metrics/`.

A hand-written Prometheus registry; `TavernMetrics` is fed by the stats recorder (so test rooms never count), the broadcast, refused `game:action`s and every HTTP response. `index.ts` serves it only when `METRICS_PORT` is set, on its own port, never on the app's port (tested). Labels are game ids, error codes and status classes only: never room or player ids, names, addresses or tokens. See `docs/deployment.md` §7.
