# Adding a game

Each game is a self-contained workspace package under `packages/games/<id>`. The platform (rooms, presence, persistence, timers and the web shell) needs no changes beyond two registry lines.

## 1. Rules: `src/logic`

Implement `GameDefinition` from `@vt/game-sdk` (see `packages/games/codenames/src/logic/game.ts`):

- **State is plain JSON.** The server stores it after every move and reloads it after restarts.
- **Logic is pure.** Use `ctx.rng` for randomness, `ctx.now` for time and `ctx.content` for word lists. Never read `Math.random`, `Date.now` or the network.
- `reduce` **returns** a `GameError` for an illegal move; the player sees its message as a toast.
- `view(state, playerId)` must strip anything that player may not see. The whole security model rests on this, so test it.
- Lobby setup (teams, seats, settings) is ordinary game actions; `ctx.isHost` tells you who may change settings. `ctx.connected(id)` (optional: absent in tests, where everyone counts as connected; bots count as connected) tells you who is online, e.g. to let the host skip only a turn nobody can play (Codenames).
- Timers: return the next deadline from `nextDeadline`, and the server calls `onDeadline` when it passes. **The timer contract:** `onDeadline` must always make progress (end the turn, mark the round timed out…), so that the returned state's `nextDeadline` is later than now, or null. If it is not, the room host logs it, allows one short back-off, then stops the timer until the next player action. An `onDeadline` that throws is logged and retried a few seconds later.
- **State stays small.** The room host rejects any change whose state exceeds about 256 KB of JSON (`MAX_STATE_JSON_LENGTH`), with a `state-too-large` error to the player who made the move, so cap your own logs, chat and history (keep the last N entries) rather than letting them grow for the life of a room.
- Optionally implement `insights` to feed the stats page: a pure `insights(before, after, action, by)` returning `InsightEvent`s (clues, guesses, outcomes) for each change. To show figures and fun facts from them, add readers for your event types in `apps/server/src/stats/figures.ts` and `aggregate.ts`, and test the real game through `apps/server/src/routes/stats.test.ts` (or with insight-shaped events in `stats/sqlite-store.test.ts`). On the page, list the word kinds your game reports in `apps/web/src/stats/word-kinds.ts` and append its id to the end of `FIXED_ORDER` in `apps/web/src/stats/palette.ts`. Figures can be `number`, `percent`, `split`, `histogram` or `matrix` (a small table drawn as a heatmap, each column shaded on its own scale). The stats recorder detects a game's start and end from its state's `phase` (`playing`, then `over`), so keep any finer stages in another field.

## 1b. Awards: `src/logic/awards.ts`

The tavern night recap (the strip of awards on every end screen and the shareable night card) is built from your `insights` events, so add `awards: <id>Awards` (an `AwardModule` from `@vt/game-sdk`, see `packages/game-sdk/src/awards.ts`) to the definition once your insights are in. Like insights, it never affects play.

- **Rules** read one finished game's events (`GameEvents`: `g.of('guess')`, players, winners) and return candidates: who earned it, the value and the runner-up for "most" rules (`leaders`, `mostBy`, `meanBy`, `topPair` apply the tie rules: 2–3 equal players share, more drop it, and zero never wins). The server scores, picks and words them; rules never throw, and read every prop defensively so events from before a prop existed simply give no candidate. Use `computeNight` (with `nightOnly`) for night totals ("spy 3 times tonight"), and `stripOnly` for anything timeout-flavoured, which never reaches the shareable card.
- **Valence and weight:** `glory` (a win or a skill), `chaos` (a funny blunder) or `gentle` (a quirk), weight 1–5. Every player's guaranteed award on the night card is never a blunder, nobody gets two, and moments (`kind: 'moment'`) compete for "moment of the night".
- **Copy:** at least two Cheeky and two Wholesome variants per rule, third person with `{who}` (or `{a}`/`{b}` for pairs), carrying a number or a fact, at most 70 characters with a 12-character name, and no banned words (`apps/server/src/recap/copy.test.ts` checks all of this). Mock the move, never the person; a blunder's Wholesome copy reframes it kindly. Player-written words go through `plain()`, and back-room names never appear in code: pass ids as `role`, `loc` or `card` params so the browser names them from the private manifest (the game's `labels` in `apps/web/src/games/private.ts`).
- **Nuggets** are the card's "by the numbers" facts, and `history(g)` gives one short line per round for the recap's "Past rounds". `stripSize` defaults to 3 lines (2 for short, frequent games). Mark a nugget `record: 'max'` (or `'min'` for fastest/quickest) when its `value` makes a good room record: the Hall of fame keeps the best one per room, and a night that beats it gets a "🆕 Room record" badge. Keep its `text` self-explanatory ("Fastest guess: 2.1 s"), since the Hall of fame shows it on its own.
- **Linked nights:** a night can span several rooms ("Same crew, new game"), so rules only ever see their own game's events; cross-game awards belong in `apps/server/src/recap/night-awards.ts`.
- **End screen:** render `<Superlatives lines={room.superlatives} />` from `@vt/ui` under the result, above the host buttons. It shows nothing while recaps are off.
- **Tests** (`awards.test.ts`): each rule's hit, no hit, ties, minimums and old events without the new props, using `fixtureGame` and `recapEv`; plus one real game played through your harness with its real `insights()` (convert with `recapEventOf`), so insights and awards never drift apart.

## 1c. Bots: `src/logic/bot.ts`

Admin playtests can fill seats with bots. Add `bot: <id>Bot` to the definition: `bot(view, ctx)` returns the one move the bot in seat `ctx.me` makes now, or null when it has nothing to do. The runner (`apps/server/src/rooms/bots.ts`) calls it after a human-like pause, from fresh state, and sends the move through the room's normal `act`, so a bot can do nothing a player couldn't.

- **View only.** The hook gets the seat's own `view()`, never the state, and `BotCtx` (`me`, `now`, a seeded `rng`, and `words(listIds)` for word lists, never questions, answers or decoys). Its type makes cheating impossible; keep it that way.
- **Pure and idempotent.** Return null once the bot has done its part (readied, voted, played), so it never repeats itself. A refused move waits for the next change before the bot tries again, unless `botInfo.retry(code)` says that refusal is worth another go (a move the bot can't judge from its view, like Inquest's Inside Man accusing a crime he doesn't know): then it tries again after its usual pause.
- **Lobby:** a bot may only seat itself (`sit`). Starting, next round, play again and every host-only step belong to the human host; bots never host.
- **Never chat, never gamble the table's chances** (solve attempts, badges). Pass wherever passing is legal. Use `pickOne`, `pickN`, `chance` and `cannedText` from `@vt/game-sdk` for random picks and filler text.
- **Roles bots can't play:** set `botInfo.note` (shown in the playtest setup) and `botInfo.setup(hostId)` (host actions the playtest runs first, e.g. giving that role to the host). Inquest does this for the Forensic Scientist.
- **Tests** (`bot.test.ts`): `playWithBots(def, seats, { seed, host, humans })` plays a whole game with a bot in every seat, on a fake clock, firing deadlines when nobody acts. Check it reaches `over` with no refused moves for a few seeds and every table size, and add a type test that the hook's first parameter is your `View`.

## 2. Guide: `src/logic/guide.ts`

Every game must ship a `GameGuide` (the `guide` field is required). The same guide renders on the "How to play" page and in the in-game rules drawer, so all games read alike. Write it for someone who has never played: say the goal first, then short setup steps, then the rules in play order, and finish with tips. Update the guide in the same PR as any rule change.

`GuideView` shows it in four tabs: **Learn** (the goal and a stepper), an optional browse tab (`tiles`), an optional **Cards** tab (`catalog`), **Rules** (the sections in three bands) and **Cheat sheet** (`reference` tables, the glossary, tips and the footer). Everything past the core fields is optional, and `apps/server/src/games/guides.test.ts` checks the shape:

- `quickStart`: 5 or 6 short bullets that cover a whole game ("what do I do now?").
- `steps`: the stepper, 4 to 7 steps, each a short title, at most 40 words of text and an `icon` (or `art`, a URL, for back-room art). The same stepper is the lobby's one-time intro for players new to the game. `shapeGuide(text, { steps: [[title, emoji], …] })` builds it from the quick start.
- Each section's `level`: `basics` (everyone should know; the first stays under 150 words), `details` (when it comes up) or `edge` (host options, leaving, timers). A section that depends on a setting gets an `option` (`{ key, label }`): in a room where it's off, it shows "Not in this game".
- `tiles`: roles, cards, heroes or locations to browse, each opening a card sheet (art, text, the win line, extra detail such as a deck list). Use them from 4 things up; for 2 or 3 roles, `roles` (with an `icon`) shows as a "Who's who" card instead. A game opens the drawer at a card with `showGuide(id)` (a tile id, or `roleAnchor(name)`: "Merlin (Good)" → `guide-role-merlin`).
- `catalog`: cards grouped under the tile they belong to (Tavern Brawl: every hero's deck), each with its art, copies and what it does in plain words, an optional `mark` ("✦ Mighty power"); groups fold, have jump-to chips and the same set and "In this game" filters (group ids are `inGame` keys). A tile's `highlights` (named abilities with their text) show in its sheet, and its `catalog` links the sheet to its group.
- `room(view, you)`: what the viewer's own `view()` says, as a `GuideContext`: a one-line summary of the room's settings, the option keys that are on, the tiles in play (with copies) for the "In this game" filter, the viewer's own role for the "You are…" card, step notes and lists for this game (Nightfall's wake order). It only ever reads the viewer's view, so it can't show anything the game doesn't.
- `presets`: setups a reader can pick on the rules page (an edition, an expansion, a line-up), each a `GuideContext`, so the same filter works there.
- Back-room games keep the real names out of the repo: the guide is `makeGuide(names)` with the plain words as the fallback, and `nameGuide(manifest)` fills names, card text and art from the private manifest (`manifestGuide` in `apps/web/src/games/private-labels.ts`). `apps/web/src/games/private.test.ts` serves made-up manifests and checks no stand-in word survives.

## 3. UI: `src/ui`

Export a React component that takes `GameUiProps<View, Action>`. Use the `@vt/ui` building blocks (`Button`, `Panel`, `Hint`, `Countdown`, `Modal`, and the lobby's `WordListPicker` and `TimerSettings`) so the game matches the rest of the site. Give `WordListPicker` a `summary` that says how your game uses the words (its default describes the Codenames board). Report `statusFor(...).yourMove` through `setYourMove` in a block-bodied effect while a game is in play, so the tab title shows "● Your turn". Design for a phone first: a player should never need to scroll through more than about one screen to act. Split dense screens into tabs, as Enigma does. Always show a `Hint` telling the viewer what to do right now.

The shell and `@vt/ui` share the patterns every game needs, so use them rather than rolling your own:

- **Who we're waiting for:** name people, never count them. `waitingFor(ids, room.players, { you })` from `@vt/game-sdk` gives "Waiting for: Ana, Ben (offline)", and `waitingForHost(room)` gives "Waiting for Ana (host) to start…". List players with `PlayerTag` (👑 for the host, an "offline" mark).
- **Timers:** give `Countdown` a `label` for what it times ("to give a clue"). Strict timers add `atZero` (what happens at 0:00); reminder timers set `soft` and an `expiredHint` (what happens now that time is up). When `onDeadline` acts for someone, record it in the log and show it with `TimeoutNote` or `timedOut()` ("⏱ Time ran out: a word was picked for you"). On a panel that stays dark in both themes (a night scene), pass `tone="dark"` so the caption stays readable.
- **Hidden information:** show a secret role, hand or note through `Peek` (`what="your role"`, an optional `cover` such as the card back, `slide` to let a slide up keep it showing, `blocked` to keep it covered whatever happens). It is the one gesture in every game: hold to look (finger, mouse, or Space/Enter), or Show/Hide for keyboards and screen readers. Pass the secret as its children: they are only rendered while showing, never hidden with CSS.
- **Confirmations:** ask with `const [confirm, dialog] = useConfirm()` (render `dialog` once), then `if (!(await confirm({ title: 'Abandon the game?', confirmLabel: 'Abandon', danger: true }))) return;`, never `window.confirm`.
- **Watchers:** call `useSpectatorPrompt(setSpectator, watching ? { text, actionLabel, action } : null)` from the game root. The shell shows "You're watching" at the top of the room, and the button runs your action, usually `revealElement(id)` on your seat control or a direct "sit" action.
- **Lobby:** wrap the Start or Deal control in `StickyBar`, so it floats at the bottom of a phone screen while its spot is out of view. Wrap the settings in `LobbySettings` with a `summary` given as its parts, most important first (counts rather than long lists): the host sees them open, guests get a summary of at most two lines, which opens to the read-only settings. Parts that don't fit the guest's screen are counted from the end ("+2 more"), never cut with an ellipsis; test a busy summary with `summaryFits` from `@vt/ui`.
- **Refusals:** put a `RefusalSlot anchor="…"` under a form and send its action with `act(action, { anchor: '…' })`. The server's refusal then appears there, or as a toast when the slot isn't on screen. It clears after a few seconds, when the player's next action works, or when its optional `resetKey` changes: pass one (a turn number, the log length) when the slot stays on screen while the game moves on.
- **Browser storage:** build every localStorage key with `storageKey(base)` from `@vt/game-sdk`. It returns `base` unchanged, except in an admin playtest, where every tab of one browser is a different seat and the key gets the seat's id, so each seat keeps its own marks, notes and tips.
- **Colours:** light mode is warm and muted, so paint with the semantic tokens from `apps/web/src/index.css`, not Tailwind's chromatic scales: surfaces `bg-panel`/`bg-card` with `ring-line`; `bg-accent text-accent-fg` (or `Button`'s `primary`) for the one main action on a screen, `soft`/`secondary` for the rest; notices as soft tints with coloured text (`bg-warn-soft text-warn-ink ring-warn-line`, likewise `info`, `danger`, `success`, `special`); teams as `team-a`/`team-b`. Keep at most one emphasised box per screen. Add `dark:` classes for dark mode as usual. `apps/web/src/light-mode.test.ts` fails on a light-mode `bg-`/`ring-`/`border-`/`outline-` class on a chromatic hue; a colour that is the game's identity (seat or role colours) may keep one with a `vt-palette` comment on its line or the line above.
- **End screens:** use `Standings` for scored games. It shows a podium, ties sharing a place, and the full final standings. Say "X wins" once, in the status line or the result panel, never both.

## Word content

Games read word lists through `ctx.content`. Set `usesWordLists: true` on the definition: each list is tagged with the games that offer it ("Used by" in the admin editor), and a room's `ctx.content` only sees the lists tagged for its game, with lists made only for that game first; lists an admin has switched off are hidden too, so a saved selection may name lists `ctx.content` no longer returns. Built-in packs live in `apps/server/word-packs/` and are shared by every word game; see CLAUDE.md for the format.

## Question content

Trivia games read admin question decks through `ctx.content`. Set `usesQuestionDecks: true` on the definition, and the room's `ctx.content` gains `questionDecks()` (the enabled decks tagged for the game: id, name, description, question count and an `adult` flag) and `questions(deckIds)` (each `Question` has `id` `<deckId>:<index>`, `deckId`, `prompt`, `answer`, `alternates` and optional `decoys`, built-in fake answers a game may use as house lies). Both methods are optional in `ContentProvider`, so check they exist and treat a missing deck as empty: a saved selection may name decks an admin has since switched off or deleted. Each deck's `games` array says which games offer it (new decks default to `["hoodwink"]`); the admin API accepts only registered games that set `usesQuestionDecks`, so register the game before tagging decks for it. The decks are protected content, so only **private** (back-room) games may use them: lobbies list decks with `GET /api/backroom/question-decks/:gameId`, which answers 404 unless the browser holds a current back-room unlock (or the admin session) and the game is private and sets `usesQuestionDecks`, and then returns summaries only. Simpler still, and what Hoodwink does: keep the summaries from `ctx.content.questionDecks()` in your state (refreshed on lobby actions), so they only ever reach players already in an unlocked room. A public trivia game would need its own endpoint and a decision about exposing deck names. The decks themselves are private and never go in the repository: tests use small made-up decks.

## Private games

A back-room game (`access: 'private'`) never names its commercial original in the repository: it uses a code name, and the admin sets the title unlocked players see (`/tavern-keeper` → Back-room titles, or `scripts/set-game-title.mjs`). Names, art and sound come from the game's private `manifest.json` in asset storage, with placeholders when there is none.

**Editions.** A second edition of an existing game (other art, other names, the same rules) is the same engine under a new id: the game exports a `define<Game>({ id, … })` factory (`defineMasquerade`, `defineHydra`), and the edition is a small package that calls it and wraps the game's UI with its own id, so it reads its own manifest and assets and gets its own lobby entry, stats and recap. Write the game's player-facing text with name tokens and copy keys from the start (Hydra's `names.ts` and `copy.ts`), so an edition can rename and reword everything from its manifest without touching code.

## 4. Register it

- Server: `apps/server/src/games/registry.ts`
- Web: `apps/web/src/games/registry.ts` (with a lazy import of the UI; keep the literal `id: '<id>',` line, which a test reads)
- Add the package to `apps/server/package.json` (devDependencies) and `apps/web/package.json` (dependencies), run `pnpm install`, and update the tests that list every game id (`apps/server/src/app.test.ts`, `apps/server/src/routes/backroom.test.ts`).

## 5. Test it

- Unit-test the rules with a seeded harness (see `packages/games/codenames/src/logic/test-utils.ts`).
- Add a Playwright spec in `e2e/` that plays one game with several browser contexts.
