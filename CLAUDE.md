# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Virtual Tavern is a private, self-hosted website for playing realtime party games with friends. It has no accounts: players join rooms through unguessable links, and only admins (who sign in with a password from the environment) can edit word lists and set the back-room password. Always call each game by its name below, never by the game it is modelled on.

- **Public** (`packages/games/`): **Codenames**, **Enigma** (team code-breaking), **Echo** (cooperative one-word clues), **Masquerade** (hidden-spy locations), **Round Table** (hidden-loyalty quests).
- **Back room** (password-gated, `packages/private-games/`, id in brackets where it differs from the name): **Reverie** (picture-clue storytelling; art in private storage), **Hoodwink** (bluffing trivia), **Royal Post** (courtship cards), Masquerade's back-room edition, **Nightfall** (one-night werewolf-style hidden roles), **Inquest** (murder deduction), **Hydra** (hidden-role election, with a themed edition), **Séance** (`seance`, cooperative ghost-and-psychics visions), **Tavern Brawl** (`tavern-brawl`, hero card brawler), **Short Fuse** (`short-fuse`, bomb cards), **Starlight** (`starlight`, picture word association), **Thorns** (`thorns`, disc bluffing), **Iconic** (`iconic`, icon-board word guessing), **Stampede** (`stampede`, answer matching), **Jeweller** (`jeweller`, gem merchants, with its Cities and Strongholds modules), **Going Once** (`going-once`, drawing and live auction), **Sketchy** (`sketchy`, drawing and fake titles), **Mosaic** (`mosaic`, tile drafting), **Encore** (`encore`, shedding cards), **Mission Control** (`mission-control`, cooperative trick-taking campaign), **Skyfire** (`skyfire`, cooperative fireworks), **Conveyor** (`conveyor`, simultaneous dish drafting), **Defuse** (`defuse`, bomb defusal: one defuser, the rest read the manual).

## Toolchain

- Node and pnpm are pinned by **Volta** in the root `package.json` (`volta` field). There is no `.nvmrc`. The `packageManager`, `engines`, the CI `setup-node` (`node-version-file: package.json`) and the `Dockerfile` `NODE_VERSION`/`PNPM_VERSION` args must all stay in sync with that pin.
- Shell commands need `export PATH="$HOME/.volta/bin:$PATH" VOLTA_FEATURE_PNPM=1`, or Volta can't find pnpm.
- pnpm is held at **11.x**. pnpm 12 ships a native binary that Volta's launcher can't run.
- TypeScript is held at **~6.0** because typescript-eslint supports `<6.1` only.
- pnpm 11 blocks dependency build scripts. Any dependency that needs one must be listed under `allowBuilds` in `pnpm-workspace.yaml`; `pnpm approve-builds <pkg>` adds it.
- Never pass `-g` through `pnpm` (`pnpm e2e -g x`): Volta takes it as "global". Use `pnpm exec playwright test --grep x`.

## Architecture

The repo is a pnpm monorepo, with ESM and strict TypeScript throughout.

- **Imports use explicit `.ts`/`.tsx` extensions.** Workspace packages export TypeScript source and are never compiled on their own: Vite bundles them for the web, and tsup bundles them into `apps/server/dist` (`noExternal: /^@vt\//`, which is why they are server *dev*Dependencies).
- **Game plugins** (`packages/games/<id>`, private ones in `packages/private-games/<id>`) implement `GameDefinition` from `packages/game-sdk/src/types.ts`. The step-by-step guide, including the member list, lobby and timer hooks, is `docs/adding-a-game.md`; the invariants are:
  - Logic is pure and its state JSON-serialisable. Randomness comes only from `ctx.rng`, time from `ctx.now`, and word lists from `ctx.content`.
  - `reduce` **returns** a `GameError` rather than throwing.
  - `view` must strip hidden information per viewer. This is the security boundary.
  - Each game package exports `/logic` and `/ui`; the UI takes `GameUiProps` (`packages/game-sdk/src/ui.ts`) and is built from `@vt/ui` primitives (`WordListPicker`, `TimerSettings`, `Modal`, `Countdown`), with `wordPool` from `@vt/game-sdk`.
  - Registries: `apps/server/src/games/registry.ts` and `apps/web/src/games/registry.ts` (private games: `apps/web/src/games/private.ts`).
  - Design every game screen to fit a phone viewport without long scrolling (tabs on phones, as Enigma's Play / Clues / Chat).
  - **Enigma** (`packages/games/enigma`): votes only resolve when every eligible teammate has picked the same code and pressed Lock in. Team chat and shared notes live in game state and are filtered per team by `view()`.
  - **Echo** (`packages/games/echo`): clue and guess matching uses `normaliseWord`/`wordKey` from `packages/game-sdk/src/words.ts` (case, accents, punctuation, plurals and simple stems). `view()` hides the secret word from the guesser until the reveal and sends them only the surviving clues, without authors or the cancelled ones (just `cancelledCount`). The UI pre-checks clues with the engine's `clueProblem` so refusals show inline.
  - **Masquerade** (`packages/games/masquerade`): players talk out loud and the app never tracks the asking. It deals (locals get only the location, the spy nothing; two spies at 7+ is a host option), names who starts, runs the round clock, then one secret vote (45 s, non-voters abstain). `namedBy` names a player only if at most as many players as there are spies have as many votes, so ties name nobody. Only a caught spy guesses the location (30 s). The logic is `defineMasquerade(config)`, so the pack is a parameter; the public pack (`src/content/`) is self-written: never copy the commercial game's locations, and never name that game. `view()` sends the location only to locals, hides the spies until the reveal (caught spies show in the guess stage) and sends only `votedCount`/`myVote` until the vote resolves. Board marks live in localStorage per table and deal.
  - **Round Table** (`packages/games/round-table`): the hidden-loyalty quest game, released in waves (wave 1: base roles, Percival, Morgana, Mordred, Oberon, the Lady of the Lake, Targeting; later waves add role records and stage hooks). Never write the commercial game's name or any reference site. `roles.ts` is the data registry (loyalty, `sees` knowledge rules, legal quest cards), `setup.ts` the tables, presets, `validateSetup`, the deal and the Assassin designation. `phase` is `lobby`/`playing`/`over` for the stats recorder and `stage` the real step (`reveal`, `propose`, `discuss`: the announced team until the leader calls the vote, `vote`, `quest`, `lady`, `assassinate`). `view()` sends your own role and only what `sees` grants, votes only once all are in, quest cards only as counts (owners are never kept), who the timer voted or played for only as counts until `over`, Lady results only to the checker, and everything at `over`. The Oberon option is the FAQ reading: Merlin doesn't see him and loyalty checks show him Good. Strict timers, the host's Skip and players who leave all use one fallback (Approve, Success, random picks). Its art is our own inline SVG (blue Good, red Evil).
- **Drawing canvas** (`packages/game-sdk/src/drawing.ts`, `packages/ui/src/drawing.tsx`; `docs/adding-a-game.md` "Drawing"): vector strokes on an 800 × 1000 page, four named colour-blind-safe pens, three widths, encoded compactly (`encodePoints`) and checked in `reduce` with `validateDrawing`. `DrawingPad` draws (undo, clear, a draft under `storageKey`, `sendBy` before a strict deadline, palm and second-finger handling); `DrawingView` shows a drawing read-only at any size. Drawings live in game state and `view()` sends only those a viewer needs.
- **Sound panel** (`packages/ui/src/sound/`): every game with sound shows the same per-player volume sliders, 0–100 % (0 is off): a master and one per type it plays (`music`, `effects`, `voice`), each with a ▶ preview of that game's own clip. Volumes are kept per device and seat (`useVolumes(game)`, `storageKey('vt.<game>.volumes')`); a sound plays at master × its type (`gainOf`). A player gets only the sliders for sound that plays on their device under the host's choice (`soundPlan`: Off, Host's device, Every device, Table screen), with `whereLine` saying where it plays; the table screen has no input, so the host sets its volumes through the game's `table-volume` action (`tableVolumeAction` in `@vt/game-sdk`). The lobby has a folded "Sound" section (`LobbySound`) and play a 🔊 corner (`SoundButton`).
- **Colours:** `apps/web/src/index.css` defines semantic tokens (`page`/`panel`/`card`/`line`, `accent`, `info`/`warn`/`danger`/`success`/`special` soft tints, `team-a`/`team-b`) that are warm and muted in light mode and map to the old stock values in dark mode, which must stay unchanged. `light-palette.css` (generated by `scripts/light-palette.mjs`, checked by its test) mutes Tailwind's chromatic scales in light mode only. UI code uses the tokens: `light-mode.test.ts` rejects light-mode chromatic fills, rings, borders and outlines, except lines marked `vt-palette` and Hydra's edition scales. See `docs/adding-a-game.md` §3.
- **Rules guides:** each game's `GameGuide` (`src/logic/guide.ts`) renders on `/rules/:gameId` and in the in-room rules drawer through `apps/web/src/components/GuideView.tsx`, in four tabs: Learn (goal + a 4–7 step stepper, which is also the lobby's one-time intro), the game's tiles (an optional `catalog` adds a Cards tab), Rules (sections banded `basics`/`details`/`edge`, greyed "Not in this game" when their `option` is off) and Cheat sheet. The drawer passes the viewer's own view to the guide's `room()`; the rules page offers `presets` instead. Back-room guides are `makeGuide(names)` + `nameGuide(manifest)` so real names, card text and art come only from the manifest (`private.test.ts` checks no stand-in survives). See `docs/adding-a-game.md` §2. Update the guide in the same change as any rule change.
- **Room host** (`apps/server/src/rooms/manager.ts`):
  - It is game-agnostic. better-sqlite3 is synchronous, so each call runs to completion and actions on a room are naturally serialised.
  - Every accepted change goes through `commit()`, which bumps `version`, persists through `RoomStore` (an optimistic version check), re-arms the game's deadline timer, and emits `changed`.
  - `realtime.ts` turns `changed` into a per-socket `room:state` snapshot holding that player's own `view()` plus `serverNow`, which clients use to correct countdowns for clock skew. An unchanged view is never re-sent. Browsers that join with `patch: true` get the whole room first, then `room:patch` updates (`packages/protocol/src/patch.ts`: only what changed in that viewer's own view since update `base`, or the whole room when that is smaller); `room-connection.ts` rebuilds the snapshot and sends `room:resync` when a patch doesn't fit. The socket is never compressed (`SOCKET_OPTIONS`, tested).
  - Rooms load lazily from SQLite, and timers re-arm on load, so play survives restarts.
  - A host who is offline for `HOST_AWAY_MS` hands the role to an online player.
  - Games never hear about disconnects unless they define the optional `playerPresence(state, id, connected, now)` hook: the manager calls it when a member's first connection opens or last one closes (several tabs count as one, bots never), and as disconnected for every member when the room loads, and commits only when the state changed.
- **Table screen** (`apps/server/src/stage.ts`, `routes/stage.ts`, web `pages/StagePage.tsx`, `pages/StageShowPage.tsx`, `stage/`, `components/TableScreen.tsx`; `docs/adding-a-game.md` "Table screen"): one per room, game-agnostic. Only the host pairs it (`room:stage-code`: 6 characters from `STAGE_CODE_ALPHABET`, 10 min, single use, in memory, at most 5 open per room) and removes it (`room:stage-remove`); `POST /api/stage/pair` (rate-limited) sets the signed `vt_stage` cookie `<roomId>.<nonce>.<back-room version>.<issued>` (7 days), valid while the room's `stage` column holds that nonce, so pairing again or removing it kills the old pass. The TV joins with `room:join` `{ roomId, role: 'stage' }`: no seat, no actions, never presence, host, sweep, live count or stats; it gets `view(state, null)` (`snapshot.role: 'stage'`, `you: ''`), and every snapshot has `stage: { present }`, which the shell turns into `GameUiProps.profile` (phones go `phone-quiet`). The pass is re-checked on every broadcast like an unlock. For a back-room room it is that room's unlock only: its own game's art and manifest and the `/backroom-assets/` code chunks, never `/api/games`, the status, decks, other games, rooms or recaps, and a new back-room word kills it. In a playtest the admin's session opens it without a code. A game opts in with a lazy `ClientGame.stage`; others get `GenericStage`.
- **Identity:** the browser keeps a secret `playerToken` in localStorage, and the server derives the public player id as `sha256(token)`, so ids shown to others can't be used to impersonate anyone.
- **Names are unique within a room** (ignoring case and spacing, `apps/server/src/rooms/names.ts`). Joining with a taken name gets the next free number ("Kim" → "Kim 2") so an invite link never bounces; renaming to a taken name is refused.
- **Player colours:** every player has a colour per room (`RoomPlayer.color`, the 16 `PLAYER_COLORS` in `packages/game-sdk/src/colors.ts`, each with a screen-reader name), saved in the room's players JSON (`rooms/colors.ts`). Joining gives a random colour nobody has (past 16 people, one of the least used); `room:recolor` changes it at any time, mid-game too (through the game's `playerJoined`), and refuses one someone else has. A game may limit its rooms to a list (`GameDefinition.colors`, `colorsOf`; Going Once's seven): joins, playtest seats and bots get only those, others are refused (`color-not-offered`), and a loaded room moves anyone outside the list onto a free one (`withColors`). `PlayerTag` draws the dot from the shell's `PlayerColors` context; the picker is in the Players drawer and behind `GameUiProps.pickColor`. Stats and recaps never see colours.
- **Room shell helpers for games** (`docs/adding-a-game.md` §3): `waitingFor`/`waitingForHost`, `Countdown` (`label`, strict/soft captions), `useSpectatorPrompt`, `act(action, { anchor })` with a `RefusalSlot` for refusals next to their control, `StickyBar` to keep Start reachable on phones, `Standings` for the shared end screen, and `EndTabs`, which splits an end screen on phones (below `lg`) into tabs so it fits a 390 × 844 phone. The snapshot's `hostAwayUntil` drives the "host is away" banner. A code chunk that fails to load after a deploy reloads the page once (`apps/web/src/lib/chunk-reload.ts`).
- **Persistence:** the Drizzle schema is in `apps/server/src/db/schema.ts`. After changing it, run `pnpm --filter @vt/server db:generate`; migrations in `apps/server/drizzle/` run when the new container starts. A failed deploy rolls back the image but not the schema, so every migration must be backward-compatible with the previous release (additive only; rename or drop in a later release). The `pre-deploy-<version>-*.db` backup is the manual restore point. Word lists are stored as a JSON array per list, with a `games` JSON array of the games that offer it (games set `usesWordLists`); `WordListRepo.forGame(id)` is the per-room `ctx.content`. An `enabled` flag (admin switch) hides a disabled list from `forGame` and the public `/api/word-lists`; admins still see it. The self-authored starter list (`starter-words.ts`) is seeded only when no lists exist.
- **Saved rooms outlive releases.** New game settings and state fields are optional, and a room saved by an older release must load (missing fields read as their defaults); keep such fallbacks until no saved room can need them.
- **Game settings** (`GameSettingsStore` in `apps/server/src/game-settings.ts`, `routes/games-admin.ts`, types in `packages/protocol/src/game-settings.ts`, the admin's `/tavern-keeper/games`): one record per game (`enabled` and `categories` for all, `title` for back-room games, `music` for games whose definition declares `music.phases`), plus the category list. All of it lives only in the database, never in code: `game_settings` in `app_settings`, while titles and music keep their old keys (`private_game_titles`, `private_game_music`). Everything that names or plays a game reads through the store; stats and recaps name games through `gameNamer` (the DB title where one is set, else the code name, applied when served). A game that is off leaves the lists and chips (`GameSummary.off`), `POST /api/rooms` refuses it (`game-off`), and the room manager's `gameOff` lets open rooms finish their game but refuses another; playtests are never stopped. `/api/games` gives each game its categories with an `order` among the categories of the games that browser can play, so a locked browser learns nothing of back-room games (tested). `scripts/set-game-title.mjs` and `scripts/set-game-categories.mjs` apply titles and categories after a game goes live.
- **Question decks** (`question_decks`, `QuestionDeckRepo` in `apps/server/src/question-decks.ts`) hold questions for games that set `usesQuestionDecks`, mirroring word lists: a `games` array (default `["hoodwink"]`; the admin API accepts only registered games that set `usesQuestionDecks`), an `enabled` switch, and `forGame(id)` merged into the per-room `ctx.content` (`roomContent`). Each question is `{prompt, answer?, alternates, sources, adult, tags, decoys?, hints?}`, with ids `<deckId>:<index>`; the rules live in `packages/protocol/src/questions.ts` and are repeated in `scripts/import-question-decks.mjs`. A deck's kind comes from its tags: **trivia** decks (games without `questionKind`, i.e. Hoodwink) need an `answer` and the `___`/`?` prompt shape (`triviaProblem`), **open** decks (games with `questionKind: 'open'`, i.e. Stampede; the script's `OPEN_GAMES` mirrors it) have no answer, alternates or decoys and optional `hints` (common answers, for playtest bots only, through `BotCtx.hints`; never in a room's state or an HTTP response except the admin detail and export); a deck tagged for both kinds is refused, and a PUT without `games` keeps the stored deck's kind. Trivia games get `ctx.content.questions()`, open games `ctx.content.openQuestions()` (prompts only). **The decks are private content: never commit them** (not even as fixtures; tests use small made-up decks). They live only in the production database, are imported with `scripts/import-question-decks.mjs` (see `docs/deployment.md`) and backed up from `/tavern-keeper`. Only back-room games use them: deck summaries are served at `GET /api/backroom/question-decks/:gameId`, which answers 404 unless the browser has the back room and the game is private with `usesQuestionDecks`. No public endpoint returns deck names, and answers, sources and decoys never appear in an HTTP response except the admin detail and export (rooms get them through `ctx.content.questions()`, and `view()` must hide them).
- **Built-in word packs** are `apps/server/word-packs/<slug>.json` (`{slug, name, description, games?, words}`; file name must match the slug; entries ≤ 20 chars, or ≤ 40 when every game in `games` is a phrase game (`PHRASE_GAMES` in `word-packs.ts`); ≥ 100 unique words). A pack with `games` is tagged only for those games; without it, for every word-list game. On startup `WordListRepo.seedPacks` adds any pack whose slug isn't in `seeded_packs` yet, exactly once, so admin edits and deletions stick. Changing a shipped pack's file does not update existing databases; add a new slug instead.
- **Content packs** (`content_packs`, `ContentPackRepo` in `apps/server/src/content-packs.ts`, admin routes in `routes/content-packs.ts`, types in `packages/protocol/src/content-packs.ts`): private content for back-room games that need more than words or questions. A game declares `contentPacks: { kinds: { <kind>: schema } }`; the admin API takes only registered private games, their declared kinds and data their schema accepts, and rooms read every enabled pack of a kind through `ctx.content.contentPacks(kind)`. **Packs are private content: never commit them** (tests use made-up packs). They are imported with `scripts/import-content-pack.mjs` (`docs/deployment.md`; `--replace` updates a pack in place, keeping its id) and managed on `/tavern-keeper`. Markup never reaches a room: pack schemas pass every string through `plainText` (`@vt/game-sdk`, plain JS in `markup.mjs` so the script imports the same file), and the script does the same before sending. Lint refuses hand-rolled tag stripping, as it does hand-rolled RegExp escapes. No route but the admin's returns pack data (`routes/content-packs.test.ts` crawls every GET route as an unlocked browser).
- **Admin stats** (`apps/server/src/stats/`): the room manager reports every change to an optional `RoomObserver`; `StatsRecorder` turns that into flat events (game start and end are detected generically from `phase`), buffers them and writes every 2 s. A game's length is its active play time (gaps over `BREAK_AFTER_MS` count 0); data and day buckets are UTC, the page shows the viewer's time zone. A failing observer is logged and never reaches play. Games may add a pure `insights(before, after, action, by)` returning `InsightEvent`s, which feed the per-game figures and fun facts in `stats/figures.ts`. Storage sits behind the `StatsStore` (write) and `StatsQueries` (read) interfaces. Rollups and raw-day queries share one aggregation (`stats/aggregate.ts`), so a rolled-up day must read exactly like its raw events (tested). Routes are `/api/admin/stats/*`, typed by `packages/protocol/src/stats.ts`, the single source of truth for both sides: `percent` figures are 0–100, and responses name every game they mention so the page needn't unlock the back room. The event props each game emits must match what `figures.ts`/`aggregate.ts` read; `routes/stats.test.ts` plays real games to keep them in line. Chart colours come from a fixed per-game order in `apps/web/src/stats/palette.ts`: append new games at the end so existing colours never shift. The page is `/tavern-keeper/stats`, a lazy chunk with ECharts in its own chunk. Retention, export and reset are covered in `docs/deployment.md`.
- **Tavern night recap** (`apps/server/src/recap/`): each game's `awards` module (`src/logic/awards.ts`, contract in `packages/game-sdk/src/awards.ts`) reads that game's own insight events. `night.ts` splits a room's `stats_events` into nights (finished games under 3 h apart, at most 16 h, split by the host's `room.wrapped`); `engine.ts`/`select.ts` score the candidates (seeded, so every viewer gets the same card) into each game's strip, the night card and "Past rounds"; `night-awards.ts` holds the cross-game awards. `RecapService` answers the member-only socket events `room:recap`, `room:wrap` and `room:recap-tone` (host only), flushing the stats recorder first. Text carries placeholders (`{p:id}`, `{role:id}`, `{loc:id}`, `{card:id}`) the browser resolves (`apps/web/src/recap/`, private names through `ClientGame.labels`). The room's tone and host time zone live in `room_recap_settings` (not a stats table, so the stats reset keeps it); the admin kill switch is `recap.enabled` in `app_settings`. Copy rules are checked by `recap/copy.test.ts`; see `docs/adding-a-game.md` §1b.
  - **Hall of fame and frozen nights** (`recap/hall.ts`): a night is frozen into `recap_nights` (both tones, plus a public-only variant when a public room's linked night reached the back room) when the host wraps it up or the room's next night starts, and a frozen card is served as it was, never recomputed. `recap_awards` feed the Hall of fame and the freshness penalties in `select.ts`; `recap_records` keep each room's best value of the nuggets marked `record`. These are not stats tables: the stats reset leaves them, a swept room's rows go with it, and "Forget me" scrubs the player from them.
  - **Linked nights** ("Same crew, new game"): `POST /api/rooms` takes an optional `nightKey`; the creator must be in a room of that night (`RecapService.linkable`), and the old room gets `room:next` so the crew can follow. A game with the optional `carry(state)` hook (Mission Control's campaign) hands the new room what the night's latest room of the same game carries, as `ctx.carried` in `create`. `night.ts` merges every room sharing the key into one night; a viewer without the back-room unlock never sees a back-room table's games, not even as a count.
  - **Save image** (`apps/web/src/recap/image.ts`): a hand-drawn Canvas 2D card (text and emoji only, never private art); neither it nor "Copy for chat" carries a link. Games show as their own emoji (`ClientGame.icon`, one per game, never 🍺 or 🎲, checked in `private.test.ts`).
- **Playtests** (`/tavern-keeper/playtest`, `routes/playtest.ts`, admin only): the admin plays any game, back-room ones included, from tabs of one browser, one tab per seat.
  - **Seats:** `minPlayers` to `seatLimit(game)` (the game's `maxSeated`, else `maxPlayers`, capped at `MAX_PLAYTEST_SEATS`). `POST /api/admin/playtests` creates the room (`rooms.playtest`, and `test: true`, so every stats and recap skip applies) and seats every seat server-side with a fresh token. Seat links carry the token in the URL fragment (`/r/<id>#seat=…&as=…`); `apps/web/src/lib/seat.ts` keeps it in sessionStorage per room id and honours it only when `/api/rooms/:id` says `playtest: true`.
  - **Gate:** a playtest is the admin's alone. `/api/rooms/:id` answers 404 to anyone else, and `room:join` answers `no-room` unless the socket carries a current `vt_admin` session (re-checked on every action and broadcast; logout revokes the session on the server, so open seat tabs lock at the next change).
  - **Stats safety:** test rooms never reach `liveRooms()` or the Live tab's socket count. `PlaytestPreview` (`rooms/preview.ts`) works out a finished game's award strip in memory and sends it as `room:playtestAwards`; nothing is written.
  - **End:** `DELETE /api/admin/playtests/:id` (or the host seat's TEST bar) sends `room:closed` and deletes the row; `sweepPlaytests` deletes playtests with no seat connected for 15 minutes.
  - **Bots:** a game's optional `bot(view, ctx)` hook (`docs/adding-a-game.md` §1c) plays a seat from that seat's own `view()` only. `BotRunner` (`rooms/bots.ts`) moves only in a playtest with a human seat connected and bots not paused, after a short pause times the speed, recomputing the move when it fires and sending it through `act`. A refused move waits for the next change (or retries when `botInfo.retry(code)` allows); `botInfo.quick(move)` marks moves that wait only a button press's pause; a runaway bot is rate-limited and then paused (`stuck`). Bot ids come from discarded tokens, so nobody can join as one; bots show as connected (`RoomPlayer.bot`) but never count as presence for host hand-off, the sweep or the live view, and never host. Codenames, Echo, Enigma, Iconic, Séance and Hydra have no bot (Inquest's bots never take the Forensic Scientist, which `botInfo.setup` gives to the host).
  - **Per-seat storage:** game UIs build localStorage keys with `storageKey(base)` from `@vt/game-sdk`, which the room shell scopes to the seat in a playtest.
- **Edge cache** (`apps/edge`, a Cloudflare Worker on `/backroom-assets/*` and `/api/backroom/assets/*`): it serves back-room code (filled from origin) and art (from the R2 binding) out of Cloudflare's cache, keyed by URL alone, but only to a browser whose `vt_edge` pass it verifies (HMAC with `EDGE_SECRET`, the unlock's lifetime, the password version from `/api/edge/backroom-version`); anything else, every error included, goes to origin untouched (origin answers without a cache header, and the server's back-room refusals, leave as `private, no-store`), so it never refuses anyone. The Worker's own Workers Caching setting stays off: it runs before the pass check, keyed by URL alone. The server issues the pass with every unlock when `EDGE_SECRET` is set (`apps/server/src/edge.ts`, its own secret, never the session secret) and clears it on lock; the shared names are in `@vt/protocol/edge`, and the Worker's `assetKey` must match the server's (tested). Setup and rollback are in `docs/deployment.md`. Opening a room has timeouts and retries on every step (`lib/retry.ts`, `JoinWatch`), each step named with a reload offer after 15 s (`LoadingStep`).
- **Metrics** (`apps/server/src/metrics/`): a hand-written Prometheus registry; `TavernMetrics` is fed by the stats recorder (so test rooms never count), the broadcast, refused `game:action`s and every HTTP response. `index.ts` serves it only when `METRICS_PORT` is set, on its own port, never on the app's port (tested). Labels are game ids, error codes and status classes only: never room or player ids, names, addresses or tokens. See `docs/deployment.md` §7.
- **Config:** `apps/server/src/config.ts` reads env vars, and its default paths resolve the same way from `src/` and `dist/`. Admin auth (`admin-auth.ts`) is a signed, httpOnly cookie bound to the current password, and login is rate-limited (keyed on `cf-connecting-ip` when the peer is a local address such as the tunnel, otherwise on the peer's own address). Errors leave through `setErrorHandler` in `app.ts` as `{ error: { code, message } }`; 5xx bodies never carry the cause.

## Testing notes

- Codenames rules tests use `harness()` and `startedGame()` from `packages/games/codenames/src/logic/test-utils.ts`, which give a seeded, deterministic game with fixed seats.
- Server tests use `testApp()` and `connect()` from `apps/server/src/test/helpers.ts`. `realtime.test.ts` plays a full game across a server restart, and `manager.test.ts` covers timers and host hand-off with fake timers.
- e2e specs fail on any uncaught browser error (`pageErrors` in `e2e/codenames.spec.ts`).
- e2e specs never assume a random outcome: they read the state from the page, use a game's rig, or rely on the test seed. Specs take `test` from `e2e/fixtures.ts` (lint enforces it), which sends a seed per test (a hash of its title) with every room it creates; the e2e server runs with `VT_TEST_SEED` (`apps/server/src/rooms/test-seed.ts`, ignored when `NODE_ENV=production`), so each room's deals, colours, game rng and bot moves come from that seed and the room's version, never from what else the server is doing. No one-off visibility checks: use web-first assertions or `expect.poll`.
- The suite marks every game's first-time lobby intro as seen (`introsSeen`, the config's `storageState`), so it never covers a spec's lobby; add a new game's id there. `e2e/guides.spec.ts` clears it to test it, and `SCREENSHOTS=1 pnpm exec playwright test e2e/guide-shots.spec.ts` shoots every guide (`GUIDE_ART` may point at a private map of local art folders).
- All e2e specs share one server. Specs that change server-wide state (the back-room password, question decks) run one at a time in the `back-room` Playwright project (`SHARED_STATE` in `playwright.config.ts`); add new ones there, and delete what they create in an `afterEach`/`finally`.
- React effects must use block bodies. Newer Chrome returns a Promise from `scrollIntoView()`, and an expression-bodied effect passes that to React as its "cleanup", which crashed the board.

## Releases and deploy

- PRs are squash-merged, so the PR title is the commit and must follow Conventional Commits (enforced by `pr-title.yml`).
- CI runs once per change, on its PR (never again on `main`): format+lint, typecheck+build and unit tests as parallel jobs, the Docker build, and the e2e suite as 4 parallel shards, each with its own server and in-memory database. `e2e/shards.ts` splits the spec files by the run times in `e2e/timings.json` (`node e2e/shards.ts --plan 4` shows the split); every spec needs a measured time there (the lint job runs `node e2e/shards.ts --check`, and the shard split refuses a spec without one): add a new spec's seconds by hand from a local run, and refresh them from a CI run's `e2e-timings-*` artifacts with `node e2e/shards.ts --update <files>`. The required check `Lint, typecheck, test, build, e2e` is a gate job that passes only when every static job and every shard pass, so keep that job name (and `Docker build`'s).
- CI fails on flaky e2e tests (`failOnFlakyTests`): a test that only passes on retry is a bug to fix. Wait for UI state with `expect.poll` or web-first assertions rather than one-off `isVisible()` checks.
- `release.yml` runs on every push to `main`. After a merged change, release-please opens or updates the Release PR (version and CHANGELOG only; opened with the workflow's token, so it gets no CI). Merging the Release PR (an admin merge, at least 60 s after its last update) makes the same workflow tag `vX.Y.Z`, publish a multi-arch image (`linux/amd64` and `linux/arm64`) to GHCR, then call `deploy.yml`, which needs approval through the `production` environment. That job joins the tailnet (Tailscale OAuth, `tag:ci`), SSHes to the server and runs `scripts/deploy.sh <version>`: back up the DB, pull, wait for health, and roll back automatically on failure. Merge to live is about 10 minutes plus the approval.
- Running `deploy.yml` by hand redeploys or rolls back to any version. One-time server, Cloudflare and GitHub setup is in `docs/deployment.md`.

## Back room (private games)

- Games with `access: 'private'` (in `packages/private-games/`) are only listed, created, joined and played by browsers that have the back room: a current `vt_backroom` unlock, or a current `vt_admin` session (the admin always has the back room, password or not). Every door (`/api/games`, titles, rooms over HTTP and socket, deck summaries, code, manifests, art, recaps, `/api/backroom/status`, which adds `admin: true` so the web shows the lobby without the door) goes through the one `hasBackroom` check in `app.ts`. The admin sets one shared password in `/tavern-keeper`; changing it, or **Sign everyone out**, bumps a version that invalidates every unlock (`apps/server/src/backroom.ts`), and admin logout revokes the admin's own. Sockets re-check the cookies on every action.
- **Never commit protected assets.** The repo is public, and `*.zip` and `private-assets/` are git-ignored. Stage files by explicit path, never `git add -A`. Art and card files live in a private Cloudflare R2 bucket; the server streams them to unlocked players at stable URLs (`/api/backroom/assets/:gameId/*`, `Cache-Control: private, max-age=1y, immutable`, so browsers keep them and the CDN never does) along with each game's `manifest.json`. Upload with `scripts/r2-upload.mjs <gameId> <folder>`, which reads credentials from `~/.config/virtual-tavern/r2-upload.env`.
- Private game UIs are registered in `apps/web/src/games/private.ts`. Vite builds them into `/backroom-assets/`, which the server serves only to unlocked browsers, with `Cache-Control: private, no-store`. Use `ProtectedImage` from `@vt/ui` for their art.

### Shared patterns of back-room games

Every game below follows these unless its entry says otherwise; the entries list only what differs or would surprise.

- **Names.** Never write the commercial game's name, its expansions', publisher, designers, illustrators, characters, card names or any reference or fan site anywhere in the repo (code, tests, docs, commits). Where a game has a real title, it is only the DB title setting (`GameSettingsStore`), falling back to the code name.
- **Ids in code, names from the manifest.** Code uses neutral ids (numbers, plain words); real names, card text, art, sound and credits come from the game's private `<id>/manifest.json` (shape in its `src/logic/manifest.ts` or `src/ui/assets.ts`, documented in `docs/deployment.md`). Without a manifest the game still plays, with numbered or plain-word placeholders and emoji, and is silent. Player-facing text uses name tokens (`{x}`, filled from the manifest's names) where a game needs renaming.
- **`view()` is the boundary.** Each game's `view.test.ts` checks every viewer at every stage with `JSON.stringify` or by comparing views of states whose hidden parts are changed, plus a seeded fuzz (500–1,000 games). Decks and piles never leave the server (counts only), other hands are counts, and everything is shown at the end.
- **State.** `phase` is `lobby`/`playing`/`over` for the stats recorder; `stage` is the real step. `insights` feed the stats page and the awards.
- **Timers.** Soft by default (a reminder and the host's Act for), strict optional. Strict timers, Act for and players who left (after `LEFT_BEAT_MS`, 3 s) all make the game's safe move (often the bot's). Where a game lets the host `remove` a player who left, that player leaves play and one player left ends the game.
- **Rulings.** "The owner's rulings" are deliberate rule choices, tested in the game's `game.test.ts` and listed in its guide; never change one without asking.
- **Testing.** A game's env test rig (`<ID>_TEST_*`) is ignored when `NODE_ENV=production` and set in `playwright.config.ts`, so its e2e spec knows the deal; `<ID>_ART=<folder>` serves local art to its screenshot spec (`STARLIGHT_ART`, `SHORT_FUSE_ART`, `JEWELLER_ART`, `MOSAIC_ART`, `ENCORE_ART`, `SKYFIRE_ART`, `CONVEYOR_ART`, `DEFUSE_ART`). Specs that import made-up packs or decks run in the `back-room` project.
- First-time tips and per-player marks use `storageKey()`.
