# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Virtual Tavern is a private, self-hosted website for playing realtime party games with friends. It hosts nineteen games: **Codenames**, **Enigma** (a team code-breaking game; only ever call it Enigma), **Echo** (a cooperative one-word-clue game; only ever call it Echo), **Masquerade** (a hidden-spy location game; only ever call it Masquerade) and **Round Table** (a hidden-loyalty quest game; only ever call it Round Table) in `packages/games/`, and **Reverie** (a picture-clue storytelling card game whose art lives in private storage; only ever call it Reverie), **Hoodwink** (a bluffing trivia game; only ever call it Hoodwink), **Royal Post** (a courtship card game; only ever call it Royal Post), Masquerade's back-room edition, **Nightfall** (a one-night werewolf-style hidden-role game; only ever call it Nightfall), **Inquest** (a murder-deduction game; only ever call it Inquest), **Hydra** (a hidden-role election game; only ever call it Hydra), **Séance** (a cooperative ghost-and-psychics vision game; only ever call it Séance, id `seance`), **Tavern Brawl** (a hero card brawler; only ever call it Tavern Brawl, id `tavern-brawl`), **Short Fuse** (a bomb-card party game; only ever call it Short Fuse, id `short-fuse`), **Starlight** (a picture word-association game; only ever call it Starlight, id `starlight`), **Thorns** (a disc-bluffing bidding game; only ever call it Thorns, id `thorns`), **Iconic** (an icon-board word-guessing game; only ever call it Iconic, id `iconic`), **Stampede** (an answer-matching party game; only ever call it Stampede, id `stampede`) and **Jeweller** (a gem-merchant card game; only ever call it Jeweller, id `jeweller`) in the password-gated back room, `packages/private-games/`. It has no accounts: players join rooms through unguessable links, and only admins (who sign in with a password from the environment) can edit word lists and set the back-room password.

## Toolchain

- Node and pnpm are pinned by **Volta** in the root `package.json` (`volta` field). There is no `.nvmrc`. The `packageManager`, `engines`, the CI `setup-node` (`node-version-file: package.json`) and the `Dockerfile` `NODE_VERSION`/`PNPM_VERSION` args must all stay in sync with that pin.
- Shell commands need `export PATH="$HOME/.volta/bin:$PATH" VOLTA_FEATURE_PNPM=1`, or Volta can't find pnpm.
- pnpm is held at **11.x**. pnpm 12 ships a native binary that Volta's launcher can't run.
- TypeScript is held at **~6.0** because typescript-eslint supports `<6.1` only.
- pnpm 11 blocks dependency build scripts. Any dependency that needs one must be listed under `allowBuilds` in `pnpm-workspace.yaml`; `pnpm approve-builds <pkg>` adds it.
- Never pass `-g` through `pnpm` (`pnpm e2e -g x`): Volta takes it as "global". Use `pnpm exec playwright test --grep x`.

## Architecture

The repo is a pnpm monorepo, with ESM and strict TypeScript throughout.

- **Imports use explicit `.ts`/`.tsx` extensions.** Workspace packages export TypeScript source and are never compiled on their own: Vite bundles them for the web, and tsup bundles them into `apps/server/dist` (`noExternal: /^@vt\//`, which is why they are server *dev*Dependencies).
- **Game plugins** (`packages/games/<id>`, private ones in `packages/private-games/<id>`) implement `GameDefinition` from `packages/game-sdk/src/types.ts`. The step-by-step guide, including the member list, lobby and timer hooks, is `docs/adding-a-game.md`; the invariants are:
  - Logic is pure and its state JSON-serialisable. Randomness comes only from `ctx.rng`, time from `ctx.now`, and word lists from `ctx.content`.
  - `reduce` **returns** a `GameError` rather than throwing.
  - `view` must strip hidden information per viewer. This is the security boundary.
  - Each game package exports `/logic` and `/ui`; the UI takes `GameUiProps` (`packages/game-sdk/src/ui.ts`) and is built from `@vt/ui` primitives (`WordListPicker`, `TimerSettings`, `Modal`, `Countdown`), with `wordPool` from `@vt/game-sdk`.
  - Registries: `apps/server/src/games/registry.ts` and `apps/web/src/games/registry.ts` (private games: `apps/web/src/games/private.ts`).
  - **Enigma** (`packages/games/enigma`): votes only resolve when every eligible teammate has picked the same code and pressed Lock in. Team chat and shared notes live in game state and are filtered per team by `view()`. On phones the play screen is split into Play / Clues / Chat tabs (`EnigmaGame.tsx`); design every game screen to fit a phone viewport without long scrolling.
  - **Echo** (`packages/games/echo`): clue and guess matching uses `normaliseWord`/`wordKey` from `packages/game-sdk/src/words.ts` (case, accents, punctuation, plurals and simple stems). `view()` hides the secret word from the guesser until the reveal and sends them only the surviving clues, without authors or the cancelled ones (just `cancelledCount`). The UI pre-checks clues with the engine's `clueProblem` so refusals show inline.
  - **Masquerade** (`packages/games/masquerade`): players talk out loud and the app never tracks the asking. It deals (locals get only the location, the spy gets nothing; two spies at 7+ is a host option), names who starts (rotating), runs the round clock, then one secret vote (when the clock ends or everyone is Ready; 45 s, non-voters abstain). `namedBy` names a player only if at most as many players as there are spies have as many votes, so ties name nobody. Only a caught spy guesses the location (30 s). The logic is `defineMasquerade(config)`, so the pack is a parameter; the public pack (`src/content/`) is self-written: never copy the commercial game's locations, and never name that game. `view()` sends the location only to locals, hides the spies until the reveal (caught spies show in the guess stage) and sends only `votedCount`/`myVote` until the vote resolves. The UI (`MasqueradeBoard`, with a `LocationDisplay` adapter) has Play / Locations / Ideas tabs; board marks live in localStorage per table and deal.
  - **Round Table** (`packages/games/round-table`): the hidden-loyalty quest game, released in waves (wave 1: base roles, Percival, Morgana, Mordred, Oberon, the Lady of the Lake, Targeting). Never write the commercial game's name or any reference site. `roles.ts` is the data registry (loyalty, `sees` knowledge rules, legal quest cards, wave), `setup.ts` the tables, presets, `validateSetup`, the deal and the Assassin designation; later waves add role records and stage hooks. `phase` is `lobby`/`playing`/`over` for the stats recorder and `stage` the real step (`reveal`, `propose`, `discuss`: the announced team until the leader calls the vote, `vote`, `quest`, `lady`, `assassinate`). `view()` sends your own role and only what `sees` grants, votes only once all are in, quest cards only as counts (owners are never kept), who the timer voted or played for only as counts until `over`, Lady results only to the checker, and everything at `over` (tested with `JSON.stringify` for every viewer at every stage). The Oberon option is the FAQ reading: Merlin doesn't see him and loyalty checks show him Good. Strict timers, the host's Skip and players who leave all use one fallback (Approve, Success, random picks). Seat marks (⭐/✕) and first-time tips live in localStorage only. Its art is our own inline SVG (blue Good, red Evil).
- **Colours:** `apps/web/src/index.css` defines semantic tokens (`page`/`panel`/`card`/`line`, `accent`, `info`/`warn`/`danger`/`success`/`special` soft tints, `team-a`/`team-b`) that are warm and muted in light mode and map to the old stock values in dark mode, which must stay unchanged. `light-palette.css` (generated by `scripts/light-palette.mjs`, checked by its test) mutes Tailwind's chromatic scales in light mode only. UI code uses the tokens: `light-mode.test.ts` rejects light-mode chromatic fills, rings, borders and outlines, except lines marked `vt-palette` and Hydra's edition scales (sky and red, which editions override). See `docs/adding-a-game.md` §3.
- **Rules guides:** each game's `GameGuide` (`src/logic/guide.ts`) renders on `/rules/:gameId` and in the in-room rules drawer through `apps/web/src/components/GuideView.tsx`, in four tabs: Learn (goal + a 4–7 step stepper, which is also the lobby's one-time intro, `GuideIntro.tsx`), the game's tiles (roles, cards, heroes, locations, each opening a card sheet; an optional `catalog` adds a Cards tab grouped by tile, as Tavern Brawl's decks by hero), Rules (sections banded `basics`/`details`/`edge`, greyed "Not in this game" when their `option` is off) and Cheat sheet (`reference` tables, glossary, tips). The drawer passes the viewer's own view to the guide's `room()` ("In your room", "You are…", "In this game"); the rules page offers `presets` instead. Back-room guides are `makeGuide(names)` + `nameGuide(manifest)` so real names, card text and art come only from the manifest (`private.test.ts` checks no stand-in survives). `guides.test.ts` checks the shape; see `docs/adding-a-game.md` §2. Update the guide in the same change as any rule change.
- **Room host** (`apps/server/src/rooms/manager.ts`):
  - It is game-agnostic. better-sqlite3 is synchronous, so each call runs to completion and actions on a room are naturally serialised.
  - Every accepted change goes through `commit()`, which bumps `version`, persists through `RoomStore` (an optimistic version check), re-arms the game's deadline timer, and emits `changed`.
  - `realtime.ts` turns `changed` into a per-socket `room:state` snapshot holding that player's own `view()` plus `serverNow`, which clients use to correct countdowns for clock skew.
  - Rooms load lazily from SQLite, and timers re-arm on load, so play survives restarts.
  - A host who is offline for `HOST_AWAY_MS` hands the role to an online player.
  - Games never hear about disconnects unless they define the optional `playerPresence(state, id, connected, now)` hook: the manager calls it when a member's first connection opens or last one closes (several tabs count as one, bots never), and as disconnected for every member when the room loads, and commits only when the state changed. Séance uses it for away seats.
- **Identity:** the browser keeps a secret `playerToken` in localStorage, and the server derives the public player id as `sha256(token)`, so ids shown to others can't be used to impersonate anyone.
- **Names are unique within a room** (ignoring case and spacing, `apps/server/src/rooms/names.ts`). Joining with a taken name gets the next free number ("Kim" → "Kim 2") so an invite link never bounces, and the shell tells the joiner; renaming to a taken name is refused with a message under the name form.
- **Player colours:** every player has a colour per room (`RoomPlayer.color`, the 16 `PLAYER_COLORS` in `packages/game-sdk/src/colors.ts`, Reverie's eight first, each with a screen-reader name), saved in the room's players JSON (rooms saved before get one on load, `rooms/colors.ts`). Joining gives a random colour nobody has (unique up to 16 people; past that, one of the least used); `room:recolor` changes it at any time, mid-game too (through the game's `playerJoined`), and refuses one someone else has. Nothing is kept in the browser, so a new room starts afresh. `PlayerTag` draws the dot from the shell's `PlayerColors` context (by name, like `BotNames`); the picker is in the Players drawer's "Change name or colour" form and behind `GameUiProps.pickColor` (Reverie's own seat). Reverie's seat colour is the player's colour (`PlayerInfo.color`); Séance keeps its psychic colours (`dot={false}` there). Stats and recaps never see colours.
- **Room shell helpers for games** (`docs/adding-a-game.md` §3): `waitingFor`/`waitingForHost` name who the game waits on, `Countdown` takes a `label` and strict/soft captions, `useSpectatorPrompt` drives the shared "You're watching" banner, `act(action, { anchor })` with a `RefusalSlot` shows refusals next to their control, `StickyBar` keeps Start reachable on phones, and `Standings` is the shared end screen. The snapshot's `hostAwayUntil` drives the "Ana (host) is away" banner, and every player is told who the new host is. A code chunk that fails to load after a deploy reloads the page once (`apps/web/src/lib/chunk-reload.ts`).
- **Persistence:** the Drizzle schema is in `apps/server/src/db/schema.ts`. After changing it, run `pnpm --filter @vt/server db:generate`; migrations in `apps/server/drizzle/` run when the new container starts. A failed deploy rolls back the image but not the schema, so every migration must be backward-compatible with the previous release (additive only; rename or drop in a later release). The `pre-deploy-<version>-*.db` backup is the manual restore point. Word lists are stored as a JSON array per list, with a `games` JSON array of the games that offer it (games set `usesWordLists`); `WordListRepo.forGame(id)` is the per-room `ctx.content`, so a room only sees lists tagged for its game. An `enabled` flag (admin switch, `PATCH /api/admin/word-lists/:id`) hides a disabled list from `forGame` (lists and words) and the public `/api/word-lists`; admins still see it. The self-authored starter list (`starter-words.ts`) is seeded only when no lists exist.
- **Game settings** (`GameSettingsStore` in `apps/server/src/game-settings.ts`, `routes/games-admin.ts`, types in `packages/protocol/src/game-settings.ts`, the admin's `/tavern-keeper/games`): one record per game with only the fields that apply (`enabled` and `categories` for all, `title` for back-room games, `music` for games whose definition declares `music.phases`), plus the category list. All of it lives only in the database, never in code: `game_settings` in `app_settings` (on/off, categories, the list), while titles and music keep their old keys (`private_game_titles`, `private_game_music`) so the release before reads them. Everything that names or plays a game reads through the store. A game that is off leaves the lists and chips (`GameSummary.off`), `POST /api/rooms` refuses it (`game-off`), and the room manager's `gameOff` lets open rooms finish their game but refuses another (leaving `over`, or a start after a game was played); playtests are never stopped. Chips: `/api/games` gives each game its categories with an `order` among the categories of the games that browser can play, so a locked browser learns nothing of back-room games (tested); several chosen chips narrow the list (a game shows only with every one), and the choices are kept per list in localStorage. `scripts/set-game-categories.mjs` applies a private categories file after a game goes live.
- **Question decks** (`question_decks`, `QuestionDeckRepo` in `apps/server/src/question-decks.ts`) hold questions for games that set `usesQuestionDecks`, mirroring word lists: a `games` array (default `["hoodwink"]`; the admin API accepts only registered games that set `usesQuestionDecks`), an `enabled` switch, and `forGame(id)` merged into the per-room `ctx.content` (`roomContent`). Each question is `{prompt, answer?, alternates, sources, adult, tags, decoys?, hints?}`, with ids `<deckId>:<index>`; the rules live in `packages/protocol/src/questions.ts` and are repeated in `scripts/import-question-decks.mjs`. A deck's kind comes from its tags (no column, no migration): **trivia** decks (games without `questionKind`, i.e. Hoodwink) need an `answer` and the `___`/`?` prompt shape on every question (`triviaProblem`, Hoodwink's rules unchanged, tested), **open** decks (games with `questionKind: 'open'`, i.e. Stampede; the script's `OPEN_GAMES` mirrors it) have no answer, alternates or decoys, any prompt shape and optional `hints` (common answers, for playtest bots only, through `BotCtx.hints`; never in a room's state or an HTTP response except the admin detail and export); a deck tagged for both kinds is refused, and a PUT without `games` keeps the stored deck's kind. Trivia games get `ctx.content.questions()` (answered questions only), open games `ctx.content.openQuestions()` (prompts only). A deck's `description` is its source or theme label in the lobby's deck picker. **The decks are private content: never commit them** (not even as fixtures; tests use small made-up decks). They live only in the production database, are imported with `scripts/import-question-decks.mjs` (see `docs/deployment.md`) and backed up from `/tavern-keeper`. Only private (back-room) games use them: deck summaries are served at `GET /api/backroom/question-decks/:gameId`, which answers 404 unless the browser has the back room (an unlock or the admin session) and the game is private with `usesQuestionDecks`. No public endpoint returns deck names, and answers, sources and decoys never appear in an HTTP response except the admin detail and export (rooms get answers and decoys through `ctx.content.questions()`, and `view()` must hide them).
- **Built-in word packs** are `apps/server/word-packs/<slug>.json` (`{slug, name, description, games?, words}`; file name must match the slug; entries ≤ 20 chars, or ≤ 40 when every game in `games` is a phrase game (`PHRASE_GAMES` in `word-packs.ts`: Iconic); ≥ 100 unique words). A pack with `games` is tagged only for those games; without it, for every word-list game. On startup `WordListRepo.seedPacks` adds any pack whose slug isn't in `seeded_packs` yet, exactly once, so admin edits and deletions stick. Changing a shipped pack's file does not update existing databases; add a new slug instead. `word-packs.test.ts` validates every pack file.
- **Admin stats** (`apps/server/src/stats/`): the room manager reports every change to an optional `RoomObserver`; `StatsRecorder` turns that into flat events (game start and end are detected generically from `phase`), buffers them and writes every 2 s. A game's length is its active play time (gaps between its `action`/`insight.*` events, a gap over `BREAK_AFTER_MS` = 60 min counting 0), however it ends; the stats page shows times of day in the viewer's time zone while data and day buckets stay UTC. A failing observer is logged and never reaches play. Games may add a pure `insights(before, after, action, by)` returning `InsightEvent`s (clues, guesses, outcomes), which feed the per-game figures and fun facts in `stats/figures.ts`. Storage sits behind the `StatsStore` (write) and `StatsQueries` (read) interfaces, so a column store can replace SQLite later. Rollups and raw-day queries share one aggregation (`stats/aggregate.ts`), so a rolled-up day must read exactly like its raw events (tested). Routes are `/api/admin/stats/*` (`routes/stats.ts`), typed by `packages/protocol/src/stats.ts`, the single source of truth for both sides: `percent` figures are 0–100, and responses name every game they mention (`games`, private ones included) so the page needn't unlock the back room. The event props each game emits must match what `figures.ts`/`aggregate.ts` read (Echo credits "the echo" from `match {a, b}` events); `routes/stats.test.ts` plays real Codenames and Echo games to keep them in line. The Words card offers only the word kinds each game reports (`apps/web/src/stats/word-kinds.ts`, with per-game labels such as Hoodwink's "Lies"), and chart colours come from a fixed per-game order in `apps/web/src/stats/palette.ts`: append new games at the end so existing colours never shift. The page is `/tavern-keeper/stats` (`apps/web/src/pages/StatsPage.tsx`, `apps/web/src/stats/`), a lazy chunk with ECharts split into its own `echarts` chunk; its e2e specs serve the typed fixtures (`stats/fixtures.ts`, kept in step with the server's figures) except one that plays a real Echo card. Retention, export and reset are covered in `docs/deployment.md`.
- **Tavern night recap** (`apps/server/src/recap/`): each game's `awards` module (`src/logic/awards.ts`, contract in `packages/game-sdk/src/awards.ts`; Masquerade Originals shares Masquerade's) reads that game's own insight events. `night.ts` splits a room's `stats_events` into nights (games under 3 h apart, at most 16 h, split by the host's `room.wrapped`; only finished games count, never one in play); `engine.ts`/`select.ts` score the candidates (seeded, so every viewer gets the same card) into each game's 2–3 line strip, the night card (moment, MVP, one award for everyone who played, at most one blunder each) and "Past rounds"; `night-awards.ts` holds the cross-game awards. `RecapService` answers the member-only socket events `room:recap`, `room:wrap` and `room:recap-tone` (host only), flushing the stats recorder first. Text carries placeholders (`{p:id}`, `{role:id}`, `{loc:id}`, `{card:id}`) the browser resolves (`apps/web/src/recap/`, private names through `ClientGame.labels`). The room's tone and host time zone live in `room_recap_settings` (not a stats table, so the stats reset keeps it); the admin kill switch is `recap.enabled` in `app_settings` (`/tavern-keeper`, `/api/admin/recap`). The snapshot's `meta` (`phase`, `gameNo`, `recap`, `tone`) lets the shell show the strip (`room.superlatives`), the 🍻 chip and the wrap-up without knowing any game. Copy rules are checked by `recap/copy.test.ts`; see `docs/adding-a-game.md` §1b.
  - **Hall of fame and frozen nights** (`recap/hall.ts`, migration 0008): a night is frozen into `recap_nights` (both tones, plus a public-only variant when a public room's linked night reached the back room) when the host wraps it up or the room's next night starts (`RecapService.observe`), and a frozen card is served as it was, never recomputed. `recap_awards` feed the Hall of fame tab and the freshness penalties in `select.ts` (last night's headline ×0.7, same award for the same player in the last 3 nights ×0.4); `recap_records` keep each room's best value of the nuggets marked `record: 'max' | 'min'` ("🆕 Room record"). These are not stats tables: the stats reset leaves them, a swept room's rows go with it, and "Forget me" scrubs the player from them.
  - **Linked nights** ("Same crew, new game"): `POST /api/rooms` takes an optional `nightKey`; the creator must be in a room of that night (`RecapService.linkable`), the recorder writes it on `room.created`, and the old room gets `room:next` so the crew can follow. `night.ts` merges every room sharing the key into one night; a viewer without the back-room unlock never sees a back-room table's games, not even as a count.
  - **Save image** (`apps/web/src/recap/image.ts`): a hand-drawn 1080×1350 Canvas 2D card (text and emoji only, never private art), pre-rendered when the sheet opens; it goes to the share sheet on touch devices, else downloads. Neither it nor "Copy for chat" carries a link. Games show as their own emoji (`ClientGame.icon`, one per game, never 🍺 or 🎲, checked in `private.test.ts`); the back room's come from its registry through `usePrivateGames`, for browsers that have it. The admin's "Recent tavern nights" on the stats Fun tab reads `/api/admin/stats/nights`.
- **Playtests** (`/tavern-keeper/playtest`, `routes/playtest.ts`, admin only): the admin plays any game, back-room ones included, from tabs of one browser, one tab per seat.
  - **Seats:** a playtest takes `minPlayers` to `seatLimit(game)` seats (the game's `maxSeated`, the most who can actually play, else its room limit `maxPlayers`; capped at `MAX_PLAYTEST_SEATS`), on the create form and for the lobby's ＋ Bot alike. `POST /api/admin/playtests` creates the room (`rooms.playtest`, JSON, and `test: true`, so every stats and recap skip applies) and seats every seat server-side with a fresh token. Seat links carry the token in the URL fragment (`/r/<id>#seat=…&as=…`); `apps/web/src/lib/seat.ts` keeps it in sessionStorage per room id and honours it only when `/api/rooms/:id` says `playtest: true`. Without a seat, a room uses the browser's own `playerToken()` exactly as before. The admin page remembers its playtests in localStorage (`vt.playtests`).
  - **Gate:** a playtest is the admin's alone. `/api/rooms/:id` answers 404 to anyone else, and `room:join` answers `no-room` unless the socket carries a current `vt_admin` session (re-checked on every action and broadcast, like the back-room unlock; logout revokes the session on the server, so open seat tabs lock at the next change). The admin session also counts as a back-room unlock everywhere (see Back room), so back-room games need no password in a playtest either.
  - **Stats safety:** test rooms never reach `liveRooms()`, and the Live tab's socket count leaves out sockets in test rooms; playtests show only as "🧪 N playtests running". `PlaytestPreview` (`rooms/preview.ts`) works out a finished game's award strip in memory from its own insights and sends it as `room:playtestAwards` ("Playtest preview: not saved" over `Superlatives`); nothing is written.
  - **End:** `DELETE /api/admin/playtests/:id` (or the host seat's TEST bar) sends `room:closed` and deletes the row; `sweepPlaytests` deletes playtests with no seat connected for 15 minutes, every 5 minutes.
  - **Bots:** a game's optional `bot(view, ctx)` hook (`docs/adding-a-game.md` §1c) plays a seat from that seat's own `view()` only. `BotRunner` (`rooms/bots.ts`) is poked on every change and moves only in a playtest with a human seat connected and bots not paused, after a 1.5–4 s pause (0.6–1.2 s for button presses) times the speed (🐢 2×, ⚡ 0.25×), recomputing the move when it fires and sending it through `act`. A refused move waits for the next change (or, when the game's `botInfo.retry(code)` allows, tries again after its pause); more than 3 bot moves a second wait; 600 in an hour pause the bots (`stuck`). Bot ids come from discarded tokens, so nobody can join as one; bots show as connected (`RoomPlayer.bot`, 🤖 through `BotNames` in `PlayerTag`) but never count as presence for host hand-off, the sweep or the live view, and never host. Bots exist for Round Table, Royal Post, Masquerade (and Originals), Nightfall, Hoodwink, Reverie, Tavern Brawl, Short Fuse, Starlight, Thorns, Stampede, Jeweller and Inquest (all but the Forensic Scientist, which `botInfo.setup` gives to the host; the Allies roles included); Codenames, Echo and Enigma need real clue words and have none yet, Iconic needs a reader of its icons and has none, and Séance and Hydra have none yet either (their playtests seat only humans).
  - **Per-seat storage:** game UIs build localStorage keys with `storageKey(base)` from `@vt/game-sdk`, which the room shell scopes to the seat in a playtest (so seat tabs keep their own marks, notes and tips).
- **Edge cache** (`apps/edge`, a Cloudflare Worker on `/backroom-assets/*` and `/api/backroom/assets/*`): it serves back-room code (filled from origin) and art (from the R2 binding, ranges straight from the bucket) out of Cloudflare's cache, keyed by URL alone, but only to a browser whose `vt_edge` pass it verifies (HMAC with `EDGE_SECRET`, the unlock's lifetime, the password version from `/api/edge/backroom-version`, re-read every 30 s); anything else, every error included, goes to origin untouched, so it never refuses anyone. Setup and rollback (delete the routes) are in `docs/deployment.md`. Opening a room has timeouts on every step (`lib/retry.ts`: a 10 s lookup tried twice, the back-room code import retried once, `JoinWatch` re-sending an unanswered join after 8 s or rejoining when no room arrives 10 s after a good one, a fresh connection when a phone wakes mid-join), each step named ("Finding your room…", "Setting up the table…", "Opening the door…") with a reload offer after 15 s (`LoadingStep`).
- **Metrics** (`apps/server/src/metrics/`): a hand-written Prometheus registry; `TavernMetrics` is fed by the stats recorder (`onEvent`/`onFlush`, so test rooms never count), the broadcast (`createRoomEvents`'s `onBroadcast`), refused `game:action`s and every HTTP response, and reads live rooms, the database size and the off-site backup status when scraped. `index.ts` serves it with `serveMetrics` on its own port only when `METRICS_PORT` is set, never on the app's port (tested). Labels are game ids, error codes and status classes only: never room or player ids, names, addresses or tokens. See `docs/deployment.md` §7.
- **Config:** `apps/server/src/config.ts` reads env vars, and its default paths resolve the same way from `src/` and `dist/`. Admin auth (`admin-auth.ts`) is a signed, httpOnly cookie bound to the current password, and login is rate-limited (keyed on `cf-connecting-ip` when the peer is a local address such as the tunnel, otherwise on the peer's own address). Errors leave through `setErrorHandler` in `app.ts` as `{ error: { code, message } }`; 5xx bodies never carry the cause.

## Testing notes

- Codenames rules tests use `harness()` and `startedGame()` from `packages/games/codenames/src/logic/test-utils.ts`, which give a seeded, deterministic game with fixed seats.
- Server tests use `testApp()` and `connect()` from `apps/server/src/test/helpers.ts`. `realtime.test.ts` plays a full game across a server restart, and `manager.test.ts` covers timers and host hand-off with fake timers.
- e2e specs fail on any uncaught browser error (`pageErrors` in `e2e/codenames.spec.ts`).
- e2e specs never assume a random outcome: they read the state from the page, use a game's rig, or rely on the test seed. Specs take `test` from `e2e/fixtures.ts` (lint enforces it), which sends a seed per test (a hash of its title) with every room it creates; the e2e server runs with `VT_TEST_SEED` (`apps/server/src/rooms/test-seed.ts`, ignored when `NODE_ENV=production`), so each room's deals, colours, game rng and bot moves come from that seed and the room's version, never from what else the server is doing. No one-off visibility checks: use web-first assertions or `expect.poll`.
- The suite marks every game's first-time lobby intro as seen (`introsSeen`, the config's `storageState`), so it never covers a spec's lobby; add a new game's id there. `e2e/guides.spec.ts` clears it to test it, and `SCREENSHOTS=1 pnpm exec playwright test e2e/guide-shots.spec.ts` shoots every guide (`GUIDE_ART` may point at a private map of local art folders).
- All e2e specs share one server. Specs that change server-wide state (the back-room password, question decks) run one at a time in the `back-room` Playwright project (`SHARED_STATE` in `playwright.config.ts`); add new ones there, and delete what they create in an `afterEach`/`finally`.
- React effects must use block bodies. Newer Chrome returns a Promise from `scrollIntoView()`, and an expression-bodied effect passes that to React as its "cleanup", which crashed the board.

## Releases and deploy

- PRs are squash-merged, so the PR title is the commit and must follow Conventional Commits (enforced by `pr-title.yml`).
- CI runs once per change, on its PR (never again on `main`): format+lint, typecheck+build and unit tests as parallel jobs, the Docker build, and the e2e suite as 4 parallel shards, each with its own server and in-memory database. `e2e/shards.ts` splits the spec files by the run times in `e2e/timings.json` (`node e2e/shards.ts --plan 4` shows the split); every spec needs a measured time there (the lint job runs `node e2e/shards.ts --check`, and the shard split refuses a spec without one): add a new spec's seconds by hand from a local run, and refresh them from a CI run's `e2e-timings-*` artifacts with `node e2e/shards.ts --update <files>`. The required check `Lint, typecheck, test, build, e2e` is a gate job that passes only when every static job and every shard pass, so keep that job name (and `Docker build`'s).
- CI fails on flaky e2e tests (`failOnFlakyTests`): a test that only passes on retry is a bug to fix. Wait for UI state with `expect.poll` or web-first assertions rather than one-off `isVisible()` checks.
- `release.yml` runs on every push to `main`. After a merged change, release-please opens or updates the Release PR (version and CHANGELOG only; opened with the workflow's token, so it gets no CI). Merging the Release PR (an admin merge, at least 60 s after its last update) makes the same workflow tag `vX.Y.Z`, publish a multi-arch image (`linux/amd64` and `linux/arm64`) to GHCR, then call `deploy.yml`, which needs approval through the `production` environment. That job joins the tailnet (Tailscale OAuth, `tag:ci`), SSHes to the server and runs `scripts/deploy.sh <version>`: back up the DB, pull, wait for health, and roll back automatically on failure. Merge to live is about 10 minutes plus the approval.
- Running `deploy.yml` by hand redeploys or rolls back to any version. One-time server, Cloudflare and GitHub setup is in `docs/deployment.md`.
