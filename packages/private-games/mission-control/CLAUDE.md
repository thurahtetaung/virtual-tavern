# Mission Control

Notes for working on this game. The repo-wide rules are in the root `CLAUDE.md`, including the shared patterns every back-room game follows; this file lists only what this game adds or does differently. Update this file in the same change as any rule, id or asset change.

## Rules and boundaries

- **Mission Control** (`packages/private-games/mission-control`, id `mission-control`) is a cooperative trick-taking campaign for 3 to 5 (2 with the dummy), with two campaigns (voyages): one with task cards from the tasks pack (`voyage-2`) and one with one-card tasks (`voyage-1`, `taskSet: 'cards'`, `onecard.ts`).
  - **Everything specific is private content:** the code knows only condition kinds (`checks.ts`) and mission rule kinds (`content.ts`); the task cards and the campaigns are content packs, and the game copies the drawn tasks and current mission into state. Order tokens are plain letters (`a1`, `o`) so the pack import's markup cleaner leaves them alone.
  - **Rules:** an attempt fails the moment a task can no longer be met, judged from the true deal; impossible task pairs are replaced (`conflicts.ts`); signals only between tricks, true positions only. The owner's rulings are in `onecard.test.ts` and the guide.
  - **Campaign:** saved per voyage key in state (`campaigns`) and carried into a "Same crew, new game" room through `carry`. Each attempt is one game for the stats recorder; a leaver stops it without counting it.
  - **`view()`:** your own hand only (none during the briefing), the dummy's face-down row as counts, secret predictions only to their holder, passed cards hidden, every dealt hand at the end.
  - **Testing:** `MISSION_CONTROL_TEST_DEAL` (e.g. `hands=p1 p2 …|b1 …;tasks=1,2`) fixes every deal and its tasks.
  - **Phones:** Play, Mission (the rules) and, in a trick, Logbook (the cards played) on the shared `TabBar`; the trick's moves sit in the fixed `StickyBar` with `mc-play`.

- **UI:** Full hands wrap without overlapping card targets on phones; the existing pick, queue and confirm controls keep their behavior.

## Assets

**Mission Control** (`node scripts/r2-upload.mjs mission-control <folder>`, dry-run first): card faces in `cards/<id>.webp` (`p1`…`p9`, `b…`, `g…`, `y…` for the four colours, `t1`…`t4` for the trumps, each with an optional small `thumb`), the card back, task-card scans in `tasks/<task id>.webp` (the ids of the tasks content pack), the tokens and the box, and a `manifest.json` of the form `{ "names": { "trump": "…", "trumps": "…", "token": "…", "captain": "…", "dummy": "…", "distress": "…", "crew": "…" }, "cards": { "p3": "cards/p3.webp" | { "art": "…", "thumb": "…" }, … }, "back": "…", "tasks": { "<task id>": { "art": "…" } }, "tokens": { "token", "used", "captain", "distress", "reminder" }, "box": "…", "logbook": { "<mission n>": { "title", "text", "rule" }, "epilogue": { … } }, "credit": "…" | { "text": "…", "url": "https://…" }, "voyages": { "<voyage key>": { "title", "names", "cards", "back", "tasks", "tokens", "box" } } }` (shape in `packages/private-games/mission-control/src/logic/manifest.ts`; a voyage's block is read before the top-level keys, and its `tokens` may add the order tokens `task-1`…`task-5`, `task-arrow-1`…`task-arrow-4` and `task-omega`). Every field is optional: without the manifest, cards are drawn from their colour symbol and value, tasks show as text and plain words stand in for the theme's names. The mission's own title, story and rule in the voyage pack win over the manifest's logbook entry. The task cards and the campaign are content packs, imported separately (Day to day). Once the art is uploaded, set the title with the `mission-control` id. The guide's steps show the box, the first task card and the first card face when the manifest has them, and the lobby's pitch shows the box.
